# yoriai
寄合システム

ローカルLLM対応デバイス(Mac mini, MacBook Pro, Mac Studioなど)が同一ネットワーク上で
自動的にお互いを発見し、各デバイスのスペックや利用可能なモデル情報を自律的に交換し合う
「組織」のようなエージェント群システムのプロトタイプです。

開発の詳しい経緯や設計判断は [DEVELOPMENT_LOG.md](./DEVELOPMENT_LOG.md) を参照してください。

## クイックスタート

Yoriaiは、同じネットワーク上のMac/Linux機を集めて「組織」を作り、
Ollama・LM Studio・MLX-LMで動くローカルLLMたちにターミナルから
話しかけて、質問したり制作を依頼したりできるツールです。

1行コマンドでインストールします(git/python3の有無を確認し、
`~/yoriai`にclone〜セットアップまでまとめて行います)。

```bash
curl -fsSL https://raw.githubusercontent.com/jun3010me/yoriai/main/install.sh | bash
```

セットアップ中の案内に沿って組織のトークンを用意したら、常駐エージェントと
対話モードをそれぞれ別のターミナルで起動します。

```bash
python3 yoriai.py
```

```bash
python3 yoriai.py --chat
```

あとは話しかけるだけです。

```
Yoriai> 富士山の標高は?
```

もっと詳しく使いたい場合は、以下の「詳しい使い方」を参照してください。

- セットアップ(手動インストールなど、他の方法)
- 実行方法(組織の作り方・トークンの使い方)
- Linux/Raspberry Piでのセットアップ
- 常駐化(自動起動)
- 対話モードで組織のメンバーに質問する(コマンド一覧など)
- タスクの性質に応じたメンバー選定・`//multi`・`//parallel`・`//agree`・`//fix`などの各コマンド
- 複数ノードによる合意形成の仕組み「対話プロトコル」と`//plan-only`コマンド

## 詳しい使い方

ここから先は、セットアップの他の方法や各コマンドの詳しい挙動など、
Yoriaiを使いこなすための詳細情報です。

### 今回のスコープ

このプロトタイプは以下を実装しています。

1. **自己紹介カードの生成**: デバイス名、OS/チップ情報、総メモリ/空きメモリ、
   インストール済みモデル一覧、ロード済み(メモリに乗っている)モデル一覧をJSONにまとめます。
   ローカルLLMバックエンドはOllama・LM Studioの両方に対応しており、どちらか一方
   (または両方)が動いていれば自動的にモデル情報を反映します。
2. **mDNSによる自動発見と自己紹介カードの交換**: 同一ネットワーク上の他のYoriaiエージェントを
   `zeroconf` (mDNS/Bonjour) で自動発見し、HTTP経由で自己紹介カードを取得してログに表示します。
3. **トークンによる参加制御(フェーズ2)**: 同じ「トークン(組織の合言葉)」を持つエージェント同士だけが
   自己紹介カードを交換します。トークンは `--init` で新規発行、`--join=<トークン>` で既存の組織に参加できます。
4. **Tailscale経由での発見(フェーズ2.5)**: mDNSは同一LAN内向けの発見として維持しつつ、
   Tailscaleで接続されたリモートデバイスも `tailscale status --json` のピア一覧を使って
   別枠で発見できるようにしています。
5. **Linux対応 + 常駐化(フェーズ4)**: macOSに加えてLinux(Raspberry Pi 4を含むDebian系など)
   でも動作します。macOSはlaunchd、Linuxはsystemdによる常駐化スクリプトも用意しており、
   SSHセッションを切っても動き続け、クラッシュ時は自動再起動されます。
   `curl -fsSL .../install.sh | bash` の1行でclone〜セットアップまで一発インストールでき
   (内部的には `./scripts/setup.sh` でvenv作成・依存関係インストール・トークン設定・
   常駐化登録をまとめて行っています)、`./scripts/update.sh` で最新コードの取得・
   依存関係の更新・常駐化サービスの再起動を、それぞれ1コマンドでまとめて行えます。
6. **組織の状態可視化(フェーズ4.5)**: `python3 yoriai.py --status` で、常駐中のエージェントに
   問い合わせて組織に参加している全メンバー(自分自身+mDNS/Tailscale経由で発見済みのピア)を
   一覧表示できます。新しくエージェントを起動したりネットワークを再スキャンしたりはしない、
   軽量な問い合わせ専用コマンドです。

タスクの割り振り、Ollama/LM Studioの自動インストール、モデル剪定などは**次フェーズ以降**の対象です。

### 動作環境

- macOS (Apple Silicon) または Linux(Raspberry Pi 4を含むDebian系などで動作確認)
  - チップ情報・メモリ情報の取得方法はOSごとに異なります
    (macOS: `sysctl` / `vm_stat`、Linux: `/proc/cpuinfo` / `/proc/meminfo`)
- Python 3.9以降
- ローカルLLMバックエンドとして、以下のどちらか(または両方)が動作していること
  - [Ollama](https://ollama.com/): `ollama serve` (通常は自動起動) が起動していること
  - [LM Studio](https://lmstudio.ai/): アプリ内の「Local Server」機能を起動していること
    (既定ポート`1234`のOpenAI互換API。`lms server start` でも起動できます)。
    **Local Serverの設定で「Require Authentication」がONになっていると、
    Yoriaiは認証ヘッダーを付けずに問い合わせるため401エラーになり、
    モデル一覧が常に空になります。OFFにしておいてください。**
  - どちらも動いていない場合、モデル一覧は空のまま自己紹介カードが生成されます(エラーにはなりません)

### セットアップ

#### 方法1: 1行コマンドでインストールする(おすすめ)

Docker/Homebrewのインストーラーと同じように、1行のコマンドでclone〜セットアップまで
まとめて行えます。

```bash
curl -fsSL https://raw.githubusercontent.com/jun3010me/yoriai/main/install.sh | bash
```

git/python3の有無を確認し、`~/yoriai`にリポジトリをclone(インストール先を変えたい場合は
`YORIAI_DIR=/path/to/dir curl ... | bash` のように環境変数で指定できます)したうえで、
そのまま下記の方法2の`setup.sh`にそのまま引き継がれ、対話的にセットアップが進みます。
既に`~/yoriai`にインストール済みの場合は、上書きはせず`./scripts/update.sh`の案内を出して終了します。

#### 方法2: セットアップスクリプトを使う

すでにcloneしてある場合や、インストール先を自分で決めたい場合はこちらを使ってください。
venv作成・依存関係インストール・トークン設定・常駐化登録までを対話的にまとめて行います
(方法1は内部的にこのスクリプトを呼んでいます)。

```bash
git clone <このリポジトリのURL>
cd yoriai
./scripts/setup.sh
```

「新しい組織を作る/既存の組織に参加する/あとで自分で設定する」を選ぶ画面が出るので、
案内に沿って進めてください。最後に「常駐化しますか?」と聞かれるので、
ログアウト後も動かし続けたい場合は `y` と答えてください(常駐化については
後述の「常駐化(自動起動)」の節も参照してください)。

#### 方法3: 手動でセットアップする

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

この場合、トークンの設定(`--init`/`--join`)や常駐化(`scripts/launchd`/`scripts/systemd`)は
このあとの節を参照して個別に行ってください。

### 実行方法

Yoriaiは起動前に「トークン(組織の合言葉)」が必要です。まずどちらかの操作でトークンを用意してください。

#### 1. 新しい組織を作る(初回の1台だけ)

```bash
python3 yoriai.py --init
```

対話的に合言葉(トークン)の入力を求められます。好きな文字列を入力するとそれが
そのまま合言葉になります。何も入力せず空欄でEnterを押すと、ランダムなトークンが
自動生成されます。合言葉を先に決めておきたい場合は、引数で直接指定することもできます。

```bash
python3 yoriai.py --init="うちの合言葉"
```

決まった合言葉/トークンはコンソールに表示されます。これをメモしておき、
同じ組織に参加させたい他の端末(Mac/Linux問わず)に共有してください。
`--init` はトークンの発行・保存のみを行い、エージェントの起動は行いません
(理由は[DEVELOPMENT_LOG.md](./DEVELOPMENT_LOG.md)の「実装上の判断メモ」を参照)。

既にトークンを発行済みの状態で `--init` を実行しても、新しいトークンには**上書きされません**。
その場合は既存のトークンがそのまま表示されるだけです。

```
既にこの組織のトークンが存在します: <既存のトークン>
この端末でYoriaiを開始するには: python yoriai.py
トークンを再発行したい場合は: python yoriai.py --init --force
```

(macOS上で実行した場合は「この端末」の部分が「このMac」と表示されます)

どうしても新しいトークンを発行し直したい場合は `--force` を付けてください。
既存の組織との接続が切れる旨の確認プロンプトが表示され、`y` と答えた場合のみ上書きされます。

```bash
python3 yoriai.py --init --force
```

#### 2. 既存の組織に参加する

```bash
python3 yoriai.py --join=<共有されたトークン>
```

指定したトークンを保存したうえで、そのままエージェントとして起動します。

#### 3. 2回目以降の起動(トークン保存済みの場合)

```bash
python3 yoriai.py
```

保存済みのトークンを使ってそのまま起動します。トークンが未設定の場合は
`--init` か `--join` を促すメッセージを表示して終了します。

このコマンドは常駐エージェント本体(自己紹介カードサーバー・mDNS/Tailscale探索・
`/chat`の提供)を起動する「キッチン」役です。ターミナルから対話的に組織の
メンバーへ質問したい場合は、これとは別に`python3 yoriai.py --chat`(「フロント」役、
後述の「対話モードで組織のメンバーに質問する」を参照)を使います。

起動すると、以下が行われます。

- 自己紹介カードをHTTPで配信するローカルサーバーが起動します
  (既定ポートは `47120`。詳細は後述の「ポートを指定したい場合」を参照)。
- mDNSは物理LANインターフェース(`en0`など)のIPアドレスのみを使って、
  `_yoriai._tcp.local.` というサービスとして自分自身を登録します
  (広告するのはトークンそのものではなく、トークンから計算したハッシュ値のみです)。
  Tailscaleの仮想インターフェース(`utun*`)は自動的に除外されます。
  どのインターフェース/IPアドレスを使っているかは起動時のログに表示されます。
- 同時に、同じサービスタイプを名乗る他のエージェントをLAN内で探索します。
  発見がない間も、10秒おきに「探索中... (現在発見数: mDNS N件 / Tailscale M件)」
  というログが出るため、正常に動作中であることを外から確認できます。mDNS側の件数は
  発見・消失のたびに更新されるリアルタイムの値です。Tailscale側の件数も後述の通り
  30秒ごとに再スキャンして更新されます。
- 発見した相手のトークン(のハッシュ値)が自分と一致する場合のみ、その `/card` エンドポイントに
  HTTPでアクセスして自己紹介カード(JSON)を取得し、以下のようにログへ表示します。
  トークンが異なる相手は「別の組織のエージェント」としてログにだけ記録し、無視します。

```
2026-08-18 10:00:00 [INFO] 🤝 MacBookPro-xxxx を発見しました (192.168.1.23:54321)
    チップ: Apple M2 Pro
    空きメモリ: 89.2GB / 総メモリ: 96.0GB
    ロード済みモデル: qwen2.5:14b
    インストール済みモデル(3件): qwen2.5:14b, llama3.1:8b, gemma2:9b
```

- さらに、Tailscaleが導入されていれば `tailscale status --json` でピア一覧を取得し、
  各ピアの `/card` エンドポイントに直接アクセスを試みます(mDNSとは別枠の仕組みです)。
  起動直後に1回、その後は30秒ごとに再スキャンします(相手がまだ起動しきっていない
  タイミングで一度失敗しても、後で自動的に見つかるようにするためです)。
  Tailscale CLIはPATH上の`tailscale`だけでなく、GUI版(App Store/dmg配布)のアプリバンドルや
  Homebrewでの典型的な設置場所も探すため、どこにインストールしていても
  「Tailscale CLIを検出しました: /Applications/...」のようにログで確認できます。
  トークンが一致する応答があった場合は mDNS と同様のログに `🌐 [Tailscale]` のラベルが付いて表示され、
  最後に「Tailscale経由でN台のエージェント候補を確認しました」とまとめて表示されます。
  問い合わせに失敗したピアがいる場合は、トークン不一致(403)なのか接続できないのかが分かるよう、
  ピアごとに失敗理由もログに表示されます。Tailscale未導入の場合はスキップされ、エラーにはなりません。

終了する場合は `Ctrl+C` を押してください。mDNSサービスの登録解除とサーバーの停止まで行われます。

#### ポートを指定したい場合

自己紹介カードサーバーの既定ポートは `47120` です。Tailscale経由の発見は
相手も既定ポートで待ち受けている前提で問い合わせるため、通常は変更不要です。

```bash
python3 yoriai.py --port 8765
```

同一マシン上で複数のエージェントを起動してテストしたい場合など、
ポートの衝突を避けたいときは `--port 0` を指定するとOSに空きポートを自動選択させられます
(この場合、Tailscale経由の発見の対象にはなりません)。

```bash
python3 yoriai.py --port 0
```

#### うまく発見できない場合のチェックポイント

- macOSのファイアウォールでPythonのネットワーク受信が許可されているか
  (初回実行時に許可ダイアログが出ることがあります)。
- 2台が同じサブネットにいるか(ルーターのゲストWi-Fi/クライアント分離設定に注意)。
- `ollama serve` が起動しているか(`curl http://localhost:11434/api/tags` で確認できます)。
- (mDNSの場合)起動時のログに物理LANインターフェースのIPアドレスが表示されているか
  (「物理LANインターフェース(en\*)を特定できなかったため」という警告が出ていないか)。
- (Tailscale経由の場合)双方とも既定ポート(`47120`)で起動しているか。

### Linux/Raspberry Piでのセットアップ

上記と同じ手順(「セットアップ」「実行方法」)がそのままLinux
(Raspberry Pi 4などのDebian系)でも使えます。事前にPython 3.9以降が
入っているか確認してください。

```bash
python3 --version
```

あとは同様に`git clone`→`pip install -r requirements.txt`→`--init`/`--join`
で起動できます。チップ情報は`/proc/cpuinfo`、メモリ情報は`/proc/meminfo`
から自動的に取得されます。mDNSの対象インターフェースの検出も、既知の
仮想インターフェース(`tailscale*`・`docker*`・`veth*`など)を除外する
方式でLinux環境に対応しています。

### 常駐化(自動起動)

SSHセッションを切っても動き続け、クラッシュ時は自動的に再起動されるように、
OSごとの常駐化スクリプトを `scripts/` 以下に用意しています。

**重要**: 常駐化スクリプトを実行する前に、必ず `--init` または `--join` で
トークンを保存しておいてください。トークン未設定のまま常駐化すると、
`python3 yoriai.py`(引数なし)が起動のたびにすぐ終了し、
launchd/systemdが再起動を繰り返してしまいます。

#### macOS(launchd)

```bash
./scripts/launchd/install.sh
```

ユーザーのLaunchAgentとして `~/Library/LaunchAgents/com.yoriai.agent.plist` に登録されます。
ログイン時に自動起動し、異常終了(クラッシュ)時は自動再起動されます
(`launchctl`のKeepAlive設定。正常終了時=`Ctrl+C`相当では再起動しません)。
ログは `~/.yoriai/logs/agent.log` / `agent.error.log` に出力されます。

```bash
# 状態確認
launchctl list | grep com.yoriai.agent

# 一時停止・再開
launchctl unload ~/Library/LaunchAgents/com.yoriai.agent.plist
launchctl load ~/Library/LaunchAgents/com.yoriai.agent.plist

# アンインストール
./scripts/launchd/uninstall.sh
```

#### Linux(systemd、Raspberry Pi 4など)

```bash
./scripts/systemd/install.sh
```

システム全体のsystemdサービス(`/etc/systemd/system/yoriai.service`)として登録されるため、
`sudo`のパスワード入力を求められます。OS起動時に自動起動し、異常終了時は
5秒後に自動再起動されます(`Restart=on-failure`)。

```bash
# 状態確認
sudo systemctl status yoriai.service

# ログ確認
sudo journalctl -u yoriai.service -f

# 一時停止・再開
sudo systemctl stop yoriai.service
sudo systemctl start yoriai.service

# アンインストール
./scripts/systemd/uninstall.sh
```

#### アップデート

Yoriaiは今後も頻繁に更新する想定のため、最新のコードを取り込む・依存関係を更新する・
(常駐化している場合は)サービスを再起動する、を1コマンドでまとめて行うスクリプトを用意しています。

```bash
./scripts/update.sh
```

- `git fetch` + fast-forwardのみのmergeでコードを更新します。ローカルに未コミットの変更や、
  originから分岐したコミットがある場合は、force的に上書きせずエラーで停止します
  (安全のため、コンフリクトの自動解決はしません)。
- `requirements.txt` の依存関係を更新します(`.venv` があればそちらの `pip` を使います)。
- 常駐化サービス(launchd/systemd)が登録されていれば自動的に再起動します。
  登録されていない場合は案内メッセージを出すだけで、フォアグラウンド実行中のプロセスを
  勝手に止めたりはしません(手動で `Ctrl+C` して再起動してください)。

### 組織の状態を確認する(--status)

常駐化した(または別のターミナルでフォアグラウンド起動中の)Yoriaiエージェントに
問い合わせて、組織に参加している全メンバーの一覧を確認できます。

```bash
python3 yoriai.py --status
```

```
=== Yoriai 組織の状態 ===

[1] junnoMac-mini [自分]
    チップ: Apple M4
    メモリ: 空き 7.5GB / 総 34.4GB
    ロード済みモデル: なし
    インストール済みモデル(5件): qwen/qwen3.8-27b, google/gemma-4-31b-qat, ...

[2] MacStudio (Tailscale経由)
    チップ: Apple M2 Ultra
    メモリ: 空き 89.0GB / 総 512.0GB
    ロード済みモデル: qwen2.5-14b
    インストール済みモデル(3件): qwen2.5-14b, llama3.1:8b, gemma2:9b
    最終確認: 5秒前

合計: 2台のエージェントが組織に参加中
```

- 自分自身は `[自分]` のラベル付きで一覧の先頭に表示されます。
- 各ピアには発見経路(`mDNS経由` / `Tailscale経由`)と最終確認時刻(何秒/分/時間前に
  応答があったか)が表示されます。同一デバイスがmDNS・Tailscaleの両方の経路で
  見えている場合は1件のメンバーに統合され、`(mDNS経由 / Tailscale経由)`のように
  両方の経路が併記されます(詳しくは後述の「同一デバイスの二重登録防止」を参照)。
- 組織に自分以外誰もいない場合は「現在、組織にはあなた1人だけです。」と表示されます。
- **新しくエージェントプロセスを起動したり、その場でネットワークを再スキャンしたりはしません。**
  既に起動している常駐プロセスに1回問い合わせるだけの軽量なコマンドです。
  そのため、常駐化している場合(またはフォアグラウンドで `python3 yoriai.py` を実行中の場合)に
  実行する必要があります。エージェントが起動していない場合は、その旨を案内して終了します。
- `--port` で常駐化しているポートを変えている場合は、`--status --port <ポート番号>` のように
  同じポート番号を指定してください(既定値は `47120` です)。

#### 同一デバイスの二重登録防止

同一LAN内かつ同じTailnet(Tailscaleのネットワーク)にいるデバイスは、mDNSと
Tailscaleの両方の経路で発見されることがあります。Yoriaiは、自己紹介カードの
`device_name`(短いホスト名)を一意な識別子とみなし、同じ`device_name`が
複数の経路で見つかった場合は1つのメンバーに統合します。`--status`の表示や
協業モードの「問い合わせ可能なメンバーがN台」といったメンバー数のカウントにも、
この統合結果が反映されます。

- 両方の経路で見えているメンバーは、実際に問い合わせ(`/chat`等)に使う
  アドレス・ポートとしてmDNS経由の情報を優先します(同一LAN内での直接発見
  であり、Tailscale経由のポーリングより低遅延・低コストと考えられるため)。
- 片方の経路の情報だけが消えても(例: mDNSからは見えなくなった)、もう片方の
  経路(Tailscale)でまだ見えている限り、メンバーとしては引き続き参加中として
  扱われます。両方の経路で見えなくなった時点で、初めて組織から消えます。

### 対話モードで組織のメンバーに質問する

Yoriaiは「キッチン(常駐エージェント)」と「フロント(対話モードのUI)」を別プロセスに
分けています。カフェに例えると、`python3 yoriai.py`(引数なし)が自己紹介カード
サーバー・mDNS/Tailscale探索・`/chat`の提供を行うキッチン、`python3 yoriai.py --chat`
が注文(質問)を取り次ぐだけのフロントです。フロントは自分ではポートのbindも
mDNS/Tailscale探索も一切行わず、既に起動しているキッチンの`/status`・`/chat`に
HTTPで問い合わせるだけのクライアントなので、キッチンを止めずに何度でも起動でき、
複数のフロントを同時に開くこともできます。

まずキッチン(常駐エージェント)を起動しておきます(systemd/launchdで常駐化済みなら
それがそのままキッチンなので、この手順は不要です)。

```bash
python3 yoriai.py
```

別のターミナル(またはタブ)で、フロント(対話モード)を起動します。

```bash
python3 yoriai.py --chat

  やり取りも含めて、`--chat`の1回の起動中は常に共有・蓄積され続けます**(例えば、

  直後の発言は、単発質問ではなく合意フェーズの続きとして扱われます。詳しくは後述の

  失敗した場合はその旨を表示して質問の入力に戻ります。
- 組織内に(自分を含めて)ロード済みモデルを持つメンバーが1人もいない場合は、
  「組織内にロード済みモデルを持つメンバーがいません。」と表示されます。
- 複数行入力のルール(下記「複数行入力」を参照)に従い、`exit` または `quit`
  を**複数行入力の最初の行として単独で**入力するか、まだ何も入力していない
  状態でCtrl+Cを押すとフロントを終了します。キッチン(常駐エージェント)
  には何も影響しません。
- キッチンが起動していない状態で `--chat` を実行した場合は、`--status`と同様に
  「実行中のYoriaiエージェントに接続できませんでした」という案内を表示して終了します。
- `--port` でキッチンのポートを変えている場合は、`--chat --port <ポート番号>` のように
  同じポート番号を指定してください(既定値は `47120` です)。

#### 起動時の案内文(ロゴ・メンバー数・色付け)

対話モード起動時の見た目を、Claude Code等のツールに近い印象にするため、
以前は1行1トピックで並んでいた長い説明文を、複数行のASCIIアートの
ロゴ・検出済みメンバー数・「基本操作」「コマンド」の2つの見出しの下に
階層立てて整理しました(上記の起動時の表示例を参照)。

- ロゴは、罫線素片で「YORIAI」を描いたfiglet風のブロック体ワードマーク
  (8行)です。区切り線の下に`G A T H E R  ・  C R E A T E`という
  サブタイトルを添えています。
- ロゴの下に、起動時点で検出できた組織のメンバー数(自分を含む)を
  `🟢 2台のメンバーが接続中(自分を含む)`のように表示します。取得に
  失敗した場合(通常は起こりませんが、キッチンとの疎通確認直後に
  タイミングよく接続できなくなった場合など)は、対話モードの起動自体は
  妨げずに「組織のメンバー数を取得できませんでした」と表示します。
- ロゴ・見出し部分は、対応する端末では色付け(ANSIエスケープシーケンス)
  して表示されます。以下のいずれかに該当する場合は自動的に色付けを
  無効にし、エスケープシーケンスの断片が表示されて崩れることのないよう
  にしています: (1) `NO_COLOR`環境変数が設定されている、(2) `TERM`が
  未設定・空、または`dumb`(高度な端末制御に対応しない、もしくは対応
  状況が不明な端末)、(3) 標準出力が端末に直接つながっていない
  (ファイル・パイプにリダイレクトされている)。
- **案内文自体は、`patch_stdout()`(バックグラウンドジョブの出力を安全に
  差し込むための仕組み)のコンテキストに入る前に出力しています。**
  実機(Raspberry Pi 4へのSSH接続)で、色付けのエスケープシーケンスが
  `?[1m?[36m`のような文字列としてそのまま表示される不具合が報告された。
  原因は、`patch_stdout()`が既定では、意図せず端末制御シーケンスを
  注入しないための安全策として書き込むテキストのESC文字を`?`に
  置換してしまうことだった。この安全策自体はLLMの応答のような信頼
  できない出力には有用なため無効にはせず、Yoriai自身が用意した固定
  テキストである案内文だけをこの安全策の外側で出力するようにして
  解決した(詳細は[DEVELOPMENT_LOG.md](./DEVELOPMENT_LOG.md)の「実装上の判断メモ」を参照)。

#### 複数行入力(テキストエディタのような編集)

対話モードは、複数行の入力全体を1つの編集可能な領域として扱う、テキスト
エディタのような入力体験に対応しています(`prompt_toolkit`ライブラリを
使用)。**Enterキーを押すとメッセージを送信**します。改行を挿入したい
場合は**Shift+Enter**を押してください(Claude Code等と同様の配置)。
上下矢印キーで、入力済みの行の間を自由に移動しながら編集できます。

```
Yoriai> //agree ToDoリストのCLIツールを作って。(Shift+Enterで改行)
storage.pyでデータの保存・読み込みを、(Shift+Enterで改行)
cli.pyでコマンドライン操作を担当する形にしたい。
(ここでEnterを押すと送信されます)
[🧭 対話プロトコルによる合意フェーズ開始: ...]
...
```

- Enterキーを押すと、その時点でバッファに入っている内容がすべて1つの
  メッセージとして送信されます。1行だけの質問も、入力→Enter、の操作で
  送信できます。
- Shift+Enterを押すと、送信されずに改行だけが挿入されます。
- **既知の制約:** 一部の端末やSSHクライアントでは、Shift+Enterが
  素のEnterと区別できないことがあります。その場合、Shift+Enterを押しても
  改行は挿入されず、その時点までの内容がそのまま送信されてしまいます。
  区別できるかどうかは端末の実装に依存し、Yoriai側で解決できる問題では
  ありません。ただし、この制約があっても対話モードから抜け出せなくなる
  ことはありません(次の「非常口(Ctrl+C 2回連続)」を参照)。
- 上下矢印キーは、まだ複数行バッファ内で移動できる行がある間はカーソルを
  その行へ移動します(2行目を書いた状態で上矢印を押すと1行目に戻って
  編集できます)。バッファの最初/最後の行まで移動すると、そこから先は
  過去に送信したメッセージの呼び出し(入力履歴、このセッション内のみ)に
  切り替わります。
- `exit`・`quit`は、**送信した内容がそれ単体である場合**(他の行を含まず、
  前後の空白を除いて`exit`または`quit`とだけ書かれている場合)にのみ、
  対話モードを終了します。メッセージの一部として`exit`という行が含まれて
  いても、通常のメッセージ本文として扱われます。
- Ctrl+Cを1回だけ押すと、その時点までに入力した内容(または、組織への
  問い合わせ中であればその処理)を破棄して新しい入力待ちに戻ります
  (対話モード自体は終了しません)。対話モードを終了したい場合は、
  `exit`・`quit`を送信するか、入力前にCtrl+D(EOF)を押してください。
  **送信キーが機能しない場合の「非常口」として、Ctrl+Cを2秒以内に2回
  連続で押すと、状況に関わらずいつでも確実に終了できます**(詳細は
  次の「非常口(Ctrl+C 2回連続)」を参照)。
- 空行で送信していた以前の仕様は廃止しました。自由に編集できる複数行
  バッファでは、メッセージの途中に意図的な空行(段落区切りなど)を
  入れられる必要があるためです。
- 2行目以降には`...`のようなプレフィックスを付けません(1行目の
  `Yoriai> `だけは維持します)。以前はreadlineベースの実装で「まだ
  入力途中である」ことを示すために`...  `という継続プロンプトを表示して
  いましたが、複数行の入力欄であること自体が視覚的に自明なため廃止し、
  Claude Code等の一般的な複数行入力欄と同様にカーソルだけが次の行へ
  移る、よりシンプルな見た目にしています。

矢印キーによる行間移動・Backspace等の基本的な編集機能は`prompt_toolkit`
ライブラリが提供するもので、GNU readlineのような1行単位の編集エンジンとは
異なり、Unicodeコードポイント単位で編集を行うため、日本語などの多バイト
文字を含む行でも文字化けが起きにくい設計になっています。

> 以前は`readline`モジュールに依存した「1行入力してEnter→空行で送信」
> という仕様でしたが、readlineは1行内のカーソル移動にしか対応しておらず、
> 上下矢印キーで前の行に戻って編集することが原理的にできませんでした。
> 実機からも、複数行にまたがる入力の改行部分に制御文字と思われる記号が
> 表示されるという報告があり、外部ライブラリを増やさない方針から一度は
> 見送っていた`prompt_toolkit`の導入を改めて検討し、採用しました
> (経緯は[DEVELOPMENT_LOG.md](./DEVELOPMENT_LOG.md)の「実装上の判断メモ」を参照)。

#### 非常口(Ctrl+C 2回連続)

**★ 送信キー(Enter)が何らかの理由で一切機能しない状況でも、Ctrl+Cを
2秒以内に2回連続で押せば、いつでも確実に対話モードを終了できます。**
対話モードの起動時にも、他の終了方法より目立つ形で案内されます。

```
Yoriai> 途中まで書いた質問文
^C
(入力を破棄しました。2秒以内にもう一度Ctrl+Cを押すと、対話モードを終了できます)
Yoriai> ^C
[⚠️ Ctrl+Cが2回連続で押されたため、対話モードを終了します]
対話モードを終了します。
```

- **入力編集中・組織への問い合わせ中(応答待ち)のどちらでCtrl+Cが発生
  しても機能します。** 例えば、1回目のCtrl+Cで応答待ちの処理を中断し、
  2回目のCtrl+Cを(中断後に戻ってきた)次の入力プロンプトで押した場合
  でも、正しく「2回連続」として検出され、対話モードが終了します。
- Ctrl+C(SIGINT)は、SSH接続を含むどのような端末経由の操作でも標準的に
  転送される割り込みシグナルです。ターミナルアプリ側のショートカットに
  奪われることがある送信キーとは異なり、この非常口は常にYoriaiまで
  届きます。
- 既存の終了方法(`exit`・`quit`の送信、入力前のCtrl+D)は、これまで
  通りそのまま使えます。Ctrl+C2回連続は、あくまでそれらが何らかの理由で
  機能しない場合の保険です。

> 実機で、Windows機からraspi4にSSH接続して対話モードを操作したところ、
> 送信キー(Alt+Enter)がSSHクライアント側(Windows側のターミナルソフト)
> の「ウィンドウの最大化/復元」ショートカットとして奪われ、Ctrl+Enterも
> (SSH経由ではWindowsネイティブコンソール向けの自動変換が働かないため)
> 機能せず、`exit`/`quit`・Ctrl+D・Ctrl+Cのいずれも反応せず対話モードから
> 一切抜け出せなくなり、最終的に別セッションからの`pkill`で強制終了する
> 必要があったという重大な不具合が報告されました。この機能はその対策
> です(経緯は[DEVELOPMENT_LOG.md](./DEVELOPMENT_LOG.md)の「実装上の判断メモ」を参照)。
>
> 【追記】その後、送信キー自体も「Enterで送信、Shift+Enterで改行」に
> 変更しました(前述の「複数行入力(テキストエディタのような編集)」を
> 参照)。この非常口は特定の送信キーに依存しない設計のため、送信キーを
> 変更した後も引き続きそのまま機能します。

#### ウェブ検索

対話モードでは、応答を担当するモデルが必要と判断した場合に、SearXNGでウェブ検索を
行ってから回答できます(モデルの持つ知識にない最新情報や、知らない固有名詞を尋ねた
場合など)。特別な操作は不要で、検索が行われている間は次のように表示されます。

```
Yoriai> 今日の東京の天気を調べて
[vm(自分) に問い合わせています... (モデル: qwen2.5-14b)]

[🔍 ウェブ検索しています...]
検索結果によると、今日の東京は...
```

- 検索を使うかどうかはモデル自身が判断します。使わなくても回答できる質問では
  検索は行われません。
- モデルがツール呼び出し(Function Calling)に対応している必要があります。
  対応していないモデルでは検索は使われず、通常のチャットとして応答します。
- 検索バックエンドは自前で用意するSearXNGインスタンスのJSON API
  (`GET {SearXNGのURL}/search?q=<検索語>&format=json`)です。SearXNG側の
  `settings.yml`で`search.formats`に`json`を含めておく必要があります
  (既定では無効になっているため、有効化しないと400エラーになります)。
  問い合わせ先のURLは環境変数`YORIAI_SEARXNG_URL`で指定できます
  (未設定時は開発時に使っているインスタンスのURLが既定値になります)。
  Tailscale経由でホスト名でアクセスする構成でも、IPアドレス直指定でも
  どちらでも構いません。SearXNGインスタンスに接続できない・タイムアウト
  した場合などはエラーにはならず「検索結果が得られなかった」ものとして
  モデルに伝わります。
- バックエンド(特にLM Studioで一部のモデルを動かした場合)によっては、ツール呼び出しが
  構造化された形で返らず、モデル自身の内部的なツール呼び出し記法(`<｜DSML｜...`など)が
  そのまま画面に表示されてしまうことがあります。この場合は
  `[⚠️ このモデルはツール呼び出しの構造化出力に対応していないようです。ツールなしで
  再試行しています...]` と表示され、自動的にツール無しで再試行して通常の回答を返します
  (検索は使われません)。

### タスクの性質に応じたメンバー選定

質問の内容に応じて、コーディング系の質問かどうかを簡易的に判定し、コーディング系
モデル(名前に`coder`などを含むモデル、例: `qwen3-coder`)を持つメンバーを優先して
問い合わせます。

```
Yoriai> このPython関数のバグを直して
[コーディング系の質問と判断し、コーディング系モデルを優先: MacStudio に問い合わせています... (モデル: qwen3-coder)]
...

Yoriai> 今日の天気は?
[空きメモリの多さで選択: junnoMac-mini に問い合わせています... (モデル: qwen2.5-14b)]
...
```

- コーディング系かどうかの判定は、コードブロック(`` ``` `` や`` ` ``で囲まれた部分)を
  含むか、「コード」「関数」「エラー」「バグ」「実装」「デバッグ」など(英語では
  `code`/`function`/`error`/`bug`/`debug`など)のキーワードを含むかで簡易的に判定します。
- コーディング系と判定した場合、コーディング系モデルを持つメンバーの中で空きメモリが
  多い順に優先します。コーディング系モデルを持つメンバーが組織に誰もいない場合は、
  通常(一般タスク)と同じ「空きメモリが多い順」に自然と一致します。
- 一般タスクはこれまで通り「空きメモリが多い順」です。
- 選定理由は問い合わせ直前のログに一言表示されます。

### 複数メンバーへの並列質問(`//multi`)

対話モードで `//multi <質問文>` と入力すると、通常の1台への問い合わせとは別に、
組織内の優先順位上位(既定3台、タスクの性質による優先順位付けも適用されます)に
同時に同じ質問を送り、それぞれの回答を候補ごとに区切って表示します。

```
Yoriai> //multi このライブラリのおすすめを教えて
[📡 空きメモリの多さで選択: 3台に同時問い合わせしています: MacStudio(モデル: qwen2.5-14b), junnoMac-mini(モデル: qwen3.8-27b), raspi4(モデル: llama3.2)]

--- junnoMac-mini (モデル: qwen3.8-27b) ---
(junnoMac-miniの回答がここに表示されます)

--- MacStudio (モデル: qwen2.5-14b) ---
(MacStudioの回答がここに表示されます)

--- raspi4 (モデル: llama3.2) ---
(raspi4の回答がここに表示されます)

Yoriai>
```

- 各候補への問い合わせは並列(バックグラウンドスレッド)で行われ、完了した候補から
  順に表示されます(通常モードのような1文字ずつのライブストリーミングではなく、
  候補ごとに回答が完成してからまとめて表示されます。理由は[DEVELOPMENT_LOG.md](./DEVELOPMENT_LOG.md)の「実装上の判断メモ」を
  参照)。
- 会話履歴には、成功した候補のうち優先順位が最も高いものの回答だけが残ります。
- 通常の質問(`//multi`を付けない場合)は、これまで通り1台にのみ送られます。

### 異なる依頼を異なるメンバーに同時に振り分ける(`//parallel`、実験1)

`//multi`が「同じ質問」を複数メンバーに投げて回答を見比べる仕組みなのに対し、
`//parallel`は「異なる依頼を、異なるメンバーに同時に振り分けて実行させ、
各回答からコード部分を抽出して手元のマシンに保存する」ための専用コマンドです。
「2台で別々のモジュールを並行開発し、手元に集約する」という実験
(下記「実験1: 2台による並行モジュール開発」)のために追加しました。

```
python yoriai.py --chat --dir ./out

Yoriai> //parallel storage.py:ToDoをJSONファイルで管理するstorage.pyを書いて | cli.py:storage.pyを使うCLIを書いて
[📡 2件のタスクを異なるメンバーに同時に依頼しています: storage.py→MacStudio(モデル: qwen2.5-coder-32b), cli.py→junnoMac-mini(モデル: qwen2.5-coder-14b)]

--- storage.py ← MacStudio (モデル: qwen2.5-coder-32b) ---
(MacStudioの回答がここに表示されます)

--- cli.py ← junnoMac-mini (モデル: qwen2.5-coder-14b) ---
(junnoMac-miniの回答がここに表示されます)

[💾 out/storage.py に保存しました (担当: MacStudio)]
[💾 out/cli.py に保存しました (担当: junnoMac-mini)]
```

- 構文は `//parallel <ファイル名1>:<依頼内容1> | <ファイル名2>:<依頼内容2> ...` です
  (`|`区切りで複数タスクを並べます)。
- タスクは「書いた順」、メンバーは「優先順位順」に並べたうえで、先頭から1対1で
  対応させて割り当てます。優先順位付けはコード生成という性質上、常に
  コーディング系タスクとして行われます(コーディング系モデルを持つメンバーが
  優先されます)。
- 各回答から最初のフェンス付きコードブロック(` ```python ... ``` `)の中身だけを
  抽出してファイルに保存します。コードブロックが見つからない場合は応答全体を
  そのまま保存します。
- 保存先ディレクトリは`--chat --dir <ディレクトリ>`で指定できます(既定値は
  カレントディレクトリ)。
- `//parallel`で送った依頼は独立した1回きりのやりとりとして扱われ、対話モードの
  会話履歴には追加されません。
- メンバーがタスク数より少ない場合は、先頭から割り当てられる分だけ実行し、
  残りはスキップした旨をログに表示します(自動リトライや1台への複数タスク
  割り当ては今回のスコープ外です)。

#### 実験1: 2台による並行モジュール開発

Yoriaiの組織機能を使い、2台のメンバーに独立したモジュールの実装を同時に
依頼し、手元のマシンに集約する実験を行いました。お題はシンプルなToDoリスト
CLIツールで、`storage.py`(データの永続化)と`cli.py`(コマンドライン
インターフェース、`storage.py`をimportする前提)をそれぞれ別のメンバーに
依頼します。

手順:

```
python yoriai.py --chat --dir .
Yoriai> //parallel storage.py:add_todo(text)->int, list_todos()->list[dict], complete_todo(id)->bool, delete_todo(id)->bool を持ち、todos.jsonに永続化するstorage.pyを書いて | cli.py:storage.pyのadd/list/complete/deleteを呼び出す、python cli.py add "text" のようなCLIを書いて(storage.pyはまだ無い前提でimportだけ用意してよい)
```

保存後、実際に統合されたモジュールを動かして確認します:

```
python cli.py add "牛乳を買う"
python cli.py list
python cli.py done 1
python cli.py list
python cli.py delete 1
```

> **検証方法についての注記**: この開発環境には実機のOllama/LM Studio/MLX-LM
> (2台のメンバー)が無いため、`//parallel`の分配ロジック(依頼の解析・
> 異なるメンバーへの正しい割り当て・コードブロック抽出・ファイル保存)は
> `tests/test_parallel_dispatch.py`で、実際のHTTP問い合わせ部分を模擬した
> テストとして検証しました。同テストの中では、想定される`storage.py`/`cli.py`の
> 実装を実際にファイルとして書き出したうえで、上記の`add`/`list`/`done`/`delete`
> の一連の動作確認コマンドを本当に実行し、2つのモジュールが問題なく連携する
> ことまで確認しています。ただし「2台の実機LLMが実際に妥当なコードを生成する
> かどうか」自体は実機での確認が別途必要です。実機での実行結果、うまく連携
> しなかった場合(関数名の不一致など)は、そのままログとして記録し、
> 自動修正までは今回のスコープに含めません。

### 制作依頼の事前すり合わせ(`//agree`、実験2)

実験1で見つかった「各メンバーへの依頼文にインターフェースを書いても、
モデルがどこまで厳密に守るかは実行してみないと分からない」という問題への
対応として、`//agree`コマンド(協業モード)を追加しました。`//parallel`が
「どのファイルを誰に頼むか」を人間が決めて渡す仕組みだったのに対し、
`//agree`はその前段として「まず1台にモジュール分割案とインターフェース
設計そのものを考えさせ、その内容をそのまま各メンバーへの実装依頼に
使う」という**合意フェーズ**を挟みます。

```
Yoriai> //agree ToDoリストのCLIツールを作って
[🧭 合意フェーズ開始: まず MacStudio (モデル: qwen2.5-coder-32b) にモジュール分割案とインターフェース設計を相談しています...]
[🧭 MacStudio の回答(合意フェーズの結果、そのまま表示)]
storage.py: ToDoリストをJSONファイルで管理するモジュール
- load_todos() -> list: todos.jsonから読み込んで返す
- add_todo(text: str) -> int: 新しいTodoを追加してIDを返す
cli.py: storageモジュールを呼び出すCLI
- storage.load_todos/storage.add_todoを呼び出す

[📐 モジュール分割案がまとまりました(2ファイル): storage.py, cli.py]
  - storage.py: load_todos() -> list: todos.jsonから読み込んで返す / add_todo(text: str) -> int: 新しいTodoを追加してIDを返す
  - cli.py: storage.load_todos/storage.add_todoを呼び出す
[📁 生成物の保存先: ./projects/todo-cli]
[🔨 実装フェーズ開始: 合意した計画に基づき、2件のファイルを異なるメンバーに並行実装させます]
[📡 2件のタスクを異なるメンバーに同時に依頼しています: storage.py→MacStudio(モデル: qwen2.5-coder-32b), cli.py→junnoMac-mini(モデル: qwen2.5-coder-14b)]
...
[💾 ./projects/todo-cli/storage.py に保存しました (担当: MacStudio)]
[💾 ./projects/todo-cli/cli.py に保存しました (担当: junnoMac-mini)]

[🔎 レビューフェーズ開始: お互いが担当外のファイルをレビューします]
[🔎 1回目のレビュー] junnoMac-mini が storage.py をレビューしています...
[junnoMac-miniがstorage.pyをレビュー] 問題なし
[🔎 1回目のレビュー] MacStudio が cli.py をレビューしています...
[MacStudio がcli.pyをレビュー] 問題なし

[✅ レビュー完了 (保存先: ./projects/todo-cli)]
```

> 生成物の保存先(`projects/<プロジェクト名>/`)の詳細は、後述の
> 「生成物の保存先」を参照してください。

- 「設計担当」には、他の候補選びと同じ優先順位ロジック(コーディング系
  タスクとして最優先の候補)を使います。
- 設計担当への相談プロンプトは、関数シグネチャ・データ形式を明記するよう
  厳密に指示します。設計担当の回答は「ファイル名: 実装すべき内容」の
  1行1ファイル形式だけでなく、ファイル名を見出しとしてその配下に関数
  シグネチャ等の詳細を箇条書きでぶら下げる階層的な形式でも正しく解析
  できます(見出しかどうかは「拡張子付きの裸のファイル名かどうか」で
  判定し、関数シグネチャのような括弧・空白を含む行は詳細としてまとめ
  られます)。
- 得られたファイル分割案は、`//parallel`と同じ仕組み
  (`_dispatch_and_save_parallel_tasks`)で異なるメンバーに並行実装させます。
  各実装担当への依頼文には、担当ファイルの説明だけでなく実装計画全体が
  埋め込まれるため、設計担当が決めたインターフェース(関数名・データ形式)が
  実装担当にそのまま伝わります。
- 設計担当の回答が期待した形式で1件も読み取れなかった場合は、その旨と
  回答全文を表示して中断します(自動リトライやフォーマットの再要求は
  今回のスコープ外)。
- 実装フェーズの後には、下記の「レビューフェーズ」が続けて実行されます
  (実装済みファイルが2件以上ある場合のみ)。

### レビューフェーズ(実験3)

実装フェーズが完了した後、各メンバーに「自分以外が担当した、もう一方の
ファイルのコード」を見せてレビューさせ、問題があれば担当メンバーに修正を
依頼する**レビューフェーズ**を追加しました。協業モード(`//agree`・自動判定)で、
実装済みファイルが2件以上ある場合に自動的に実行されます。

- レビュー担当は、実装計画全体(合意した内容)と、自分が担当した
  ファイルのコードを踏まえたうえで、以下の観点でレビューします:
  1. 合意した関数名・引数・戻り値の型・データ形式と、実際のコードが
     一致しているか
  2. 自分が担当したファイルと正しく連携できそうか
  3. 例外処理の欠如・タイポなど、コードとして明らかな不備がないか
  - 自分が担当したファイル以外との連携を確認したい場合は、後述の
    「レビュー担当によるファイル読み取り(read_fileツール)」で実際の
    ファイルの中身を確認したうえで判断できます。
- レビュー結果は`[{メンバー名}が{ファイル名}をレビュー] 問題なし`、
  または`問題あり: {具体的な指摘}`という形式で画面に表示されます。
- 「問題あり」の指摘があった場合、指摘内容をそのままファイルの担当
  メンバーに伝えて修正を依頼し、修正版のコードでファイルを上書き保存
  したうえで、もう一度だけ再レビューします。
- **機械的な構文チェック(LLMによる内容レビューより前に実行)**: `.py`で
  終わるファイルについては、LLMによる内容レビューの前に必ず
  `ast.parse`による構文チェックを行います。

  ```
  [🔍 構文チェック: OK]
  [{メンバー名}がcli.pyをレビュー] 問題なし
  ```

  構文エラーがある場合は、LLMのレビューを待たずに即座に「問題あり」
  として扱い、そのままLLMには問い合わせません:

  ```
  [❌ 構文チェック: IndentationError (8行目: unexpected indent)]
  [🔧 {担当メンバー名} に cli.py の修正を依頼しています...]
  ```

  構文エラーのないコードだけを内容レビューの土俵に載せることで、
  「メソッドチェーンの括弧漏れによる`IndentationError`が、LLMの
  内容レビューでは『問題なし』と誤判定されてそのまま確定してしまう」
  という実機での不具合を防ぎます。構文チェックの再試行(修正後の
  再チェック)も、上記の「最大2回のレビュー」の枠内に含まれます
  (構文エラーが2回連続で残った場合は、LLMによる内容レビューは一度も
  行われないまま「未解決」として打ち切られます)。`.py`以外のファイル
  では`ast.parse`がPython専用のため構文チェック自体を行わず、これまで
  通りLLMによる内容レビューだけを行います。
- **暴走防止**: 1ファイルにつき「1回目のレビュー」→(問題があれば)
  「修正」→「修正後の再レビュー」という最大2回のレビューまでで、
  それ以上は自動的に繰り返しません。画面には`[🔎 1回目のレビュー]`
  `[🔎 修正後の再レビュー]`とラベルが表示され、今どちらの段階かが
  分かるようになっています。再レビューでも問題が残った場合は、そこで
  打ち切り、`[⚠️ 未解決の指摘が残っています: <ファイル名>]`と表示します。
- **応答の長さにも上限があります**: バックエンド(Ollama/LM Studio/
  MLX-LM)への問い合わせには、応答トークン数の上限(`CHAT_MAX_OUTPUT_TOKENS`、
  既定8192)を毎回指定しています。複雑な指摘(複数の問題点を同時に含む
  修正依頼など)を受けたモデルが、生成をやめる判断ができずに応答を
  延々と続けてしまう不具合が実機で報告されたための対応です。この上限に
  達して応答が途中で打ち切られた場合、`[⚠️ ... 打ち切りました]`と
  表示したうえで、その回の問い合わせ自体を通常の失敗と同じ扱いにします
  (修正依頼であれば、既存の「最大2回のレビュー」の枠を1回消費して
  未解決として報告します。新たな再試行ループは追加していません)。
- そのレビューフェーズが処理した範囲(=実装フェーズに実際に到達した
  ファイル)がすべて最終的に「問題なし」になった時点で、
  `[✅ レビュー完了(今回レビュー対象の<件数>ファイル、保存先: <ディレクトリ>)]`
  と表示します。**ただしこれは「レビューフェーズが担当した範囲での結論」
  であり、計画全体が完了したことの保証ではありません**(詳しくは次の
  「タスクチェックリスト」を参照)。
- 実装済みファイルが1件以下(候補不足などで並行実装が1件しかできなかった
  場合)は、担当外のレビュー担当が存在しないため、レビューフェーズ自体を
  スキップします。

### レビュー担当によるファイル読み取り(read_fileツール)

レビュー担当には、これまで自分が担当したファイルの中身だけをプロンプトに
直接埋め込んでいましたが、これは「伝聞情報」であり、レビュー対象が
自分の担当ファイル以外(例: 別のメンバーが担当したファイル)と正しく
連携しているかを確認したい場合には不十分でした(実機で、cli.pyのレビュー
時に「storage.pyがconfig.pyを正しく使っているか確認できない」という
指摘が実際に出ました)。Claude Code自身が推測ではなく実際にファイルを
読みに行ってから判断するのと同様に、レビュー担当にも`read_file`という
関数呼び出し(function calling)の選択肢を与え、必要と判断した場合に
実際のファイルの中身を確認してから最終判定を出せるようにしました。

```
[🔎 1回目のレビュー] junnoMac-mini が cli.py をレビューしています...
[📖 junnoMac-mini が storage.py を読みに行っています...]
[junnoMac-miniがcli.pyをレビュー] 問題なし
```

- レビュー担当のモデルが「storage.pyの中身を確認したい」と判断すると、
  `read_file(filename="storage.py")`というツール呼び出しが行われ、その
  時点でプロジェクトに実際に保存されているstorage.pyの中身がそのまま
  返されます。レビュー担当はその内容を踏まえて、改めて「問題なし」
  または「問題あり」の最終判断を下します。
- 読み取り対象は、自分が担当したファイルに限らず、プロジェクト内で
  その時点までに実装済みの任意のファイルです。
- まだ実装されていないファイル名を指定した場合は、エラーにはせず
  「そのファイルはまだ存在しません(未実装です)」という情報がそのまま
  モデルへの回答として返されます。
- 無駄な呼び出しの繰り返しを防ぐため、1回のレビューにつき`read_file`の
  呼び出しは最大3回までに制限されます。
- ツール呼び出しの様子(何を読みに行っているか)は`[📖 ...を読みに行って
  います...]`という形で画面に表示され、依頼の「ツール呼び出しのログが
  確認できる」という動作確認要件に対応しています。
- **`read_file`は呼ばれた瞬間にディスクを読み直します**: タスクキュー
  方式では複数のファイルが並行して実装されるため、あるファイルの
  レビューが進行している間に、別のワーカースレッドが新しいファイルを
  完成させることがあります。`read_file`は依頼の発行時点のスナップ
  ショットを使い回すのではなく、実際に呼び出されたその瞬間のプロジェクト
  ディレクトリを都度読み直すため、レビュー担当が確認した時点で既に完成
  していれば正しく「存在する」と判定されます(実機で、この反映が
  行われず「存在しない」と誤判定されてレビュー往復の上限を無駄に使い
  切ってしまう不具合が報告されたための対応)。

### タスクキュー方式による実装フェーズ(依頼1)

実装フェーズは、実験1・実験2の頃は「合意フェーズが決めたファイル数と
メンバー数を先頭から1対1で対応させ、メンバー数を超えた分は切り捨てる」
という単純な割り当てでした。実機での運用で、合意フェーズが4ファイル
構成を提案してもメンバーが2台しかいない場合、後半の2ファイルが永遠に
実装されないという問題が明らかになったため、実装フェーズを**タスクの
待ち行列(キュー)**として扱う方式に変更しました。

- **メンバー数を超えても全タスクが実装される**: タスク数がメンバー数を
  超える場合、最初はメンバー数ぶんだけタスクを割り当てて実装を開始し、
  いずれかのメンバーの実装+レビューが完了したら、そのメンバーに次の
  タスクをキューから割り当てます。これを全タスクが完了するまで繰り返す
  ため、上記の例のように2台のメンバーでも4ファイルすべてが最終的に
  実装されます(以前のような「切り捨て」は発生しません)。
- **タスクの重さ(実装の複雑さ)に応じた優先度**: キューは、合意フェーズが
  そのファイルについて書いた説明文の長さを「重さ」の簡易的な代理指標として
  使い、重い順に並べます。候補メンバーの一覧は空きメモリの多い順に並んで
  いるため、キューの先頭(最も重いタスク)から順に、空きメモリの多い
  メンバーへ初期割り当てされる形になります。
- **進行状況の逐次表示**: タスクが割り当てられるたびに、初回の割り当ては
  `[📋 タスクキュー: <メンバー名> に <ファイル名> を割り当てました (残り
  <件数>件: <ファイル名一覧>)]`、手が空いての再割り当ては`[🙌 <メンバー名>
  の手が空いたため、次のタスク <ファイル名> を割り当てます (残り<件数>件:
  <ファイル名一覧>)]`という形式で表示されます。
- **タスクチェックリストとの連動**: キューによる実装・レビューの進行は、
  上記の例のように、既存のタスクチェックリスト機能とそのまま連動して
  います。キューによって全タスクが実行された場合は、最終確認で正しく
  `[✅ 全タスク完了]`と表示されます。
- **レビュー担当**: 各メンバーは「実装→(担当外の別メンバーに)レビュー
  依頼→(必要なら)修正→再レビュー」というサイクルの両方が完了して
  初めて、次のタスクをキューから取ります。レビュー担当は「自分以外の
  最初のメンバー」という固定選択です。メンバーが1台しかいない場合は
  担当外のレビュー担当を選べないため、そのファイルのレビューはスキップ
  されます(実装だけは行われ、レビューはタスクチェックリスト上
  「未完了」のまま残ります)。
- **どの行がどのタスクのものか、`[<ファイル名>]`タグで判別できます**:
  複数のメンバーが並行して作業するため、画面には異なるタスクの出力が
  入り交じって表示されることがあります。上記の例のように、実装フェーズ・
  レビューフェーズの出力行はすべて先頭に`[<対象ファイル名>]`というタグが
  付き、1行単体でもどのタスクの結果かを判別できます。また、複数行にわたる
  出力(実装結果のコードプレビューなど)は、途中で他タスクの出力が
  割り込まないよう、1つのまとまりとして出力されます。

### タスクチェックリスト(組織が自ら立てた計画への責任)

合意フェーズが決めるモジュール分割案(ファイル構成)は、人間が「〇個の
ファイルにしてください」と直接指定したものではなく、設計担当メンバー自身が
「この構成が適切です」と提案したものです。そのため、Yoriaiは「組織自身が
生み出した計画であっても、組織側がそれを完遂する責任を負う」という考え方に
基づき、合意フェーズが確定した瞬間にその計画を**必ず完遂すべきタスクリスト**
として固定し、Claude CodeのTodoWriteと同様に進行状況を追跡します。実装
フェーズ・レビューフェーズがそれぞれ「自分の担当範囲では完了した」と
表示していても、計画全体で見て未完了の項目が残っていれば、最後に必ずそれを
検出して正直に報告します。

```
[📝 タスク状況(組織が自ら立てた計画)]
✅ storage.py の実装
✅ storage.py のレビュー
✅ cli.py の実装
✅ cli.py のレビュー
✅ utils.py の実装
⬜ utils.py のレビュー
⬜ config.py の実装
⬜ config.py のレビュー

[⚠️ 未完了のタスクが残っています: config.py の実装, config.py のレビュー]
```

- タスクリストは、ファイルごとに「`<ファイル名> の実装`」「`<ファイル名>
  のレビュー`」の2項目で構成され、`⬜`(未着手)・`⏳`(進行中)・`✅`(完了)の
  3状態で管理されます。
- モジュール分割案が確定した直後(全項目`⬜`)と、最終確認時の、少なくとも
  2つのタイミングでタスクリスト全体を画面に表示します。実装フェーズの
  進行中は、後述の「タスクキュー方式による実装フェーズ」が、タスクが
  割り当てられるたびに`[📋 タスクキュー: ...]`/`[🙌 ...の手が空いたため...]`
  という個別メッセージで都度進捗を表示します。
- **【最も重要な仕組み】最終確認**: 実装フェーズ・レビューフェーズが
  すべて終わった段階で、必ずこのタスクリスト全体を確認します。1つでも
  未完了(`⬜`または`⏳`)の項目が残っている場合、`✅`系のメッセージは
  一切表示せず、代わりに`[⚠️ 未完了のタスクが残っています: <未完了項目の
  一覧>]`と、何が終わっていないかを明示して報告します。すべて完了して
  いる場合のみ`[✅ 全タスク完了 (保存先: <ディレクトリ>)]`と表示します。
- **タスクキュー方式導入後の位置づけ**: 以前は、合意フェーズが決めた
  ファイル数がメンバー数を超える場合、候補不足で一部のファイルが実装
  フェーズに到達しないまま「未完了」として残り続けることがありました
  (このタスクチェックリスト自体は、その不具合を実機で報告を受けて
  追加した機能です)。後述の「タスクキュー方式による実装フェーズ」導入後は、
  メンバーの手が空くたびに次のタスクが割り当てられるため、メンバー数が
  タスク数より少なくても最終的に全タスクが実装・レビューされ、
  `[✅ 全タスク完了]`に到達するのが通常の流れになります。ただし、メンバーが
  1台しかいない場合の「レビュースキップ」(後述)や、問い合わせ自体の
  失敗など、依然として未完了のまま残るケースはあり、そうした場合には
  このタスクチェックリストの最終確認が引き続き正直に検出します。

### 計画とのファイル名の整合性チェック

実機で、「高校生向けのHTML/CSSの学習サイトを作って」という依頼に対し、
設計担当が`editor.js`/`preview.js`という2ファイルを計画に挙げていながら、
`index.html`の説明文の中では両方をまとめて`script.js`という(計画には
存在しない)名前で言及してしまい、実装された`index.html`が実際に
`script.js`を読み込むコードになってしまう不具合が報告されました。
`script.js`というファイル自体が最初から作られる予定のないものだったため、
レビュー→修正→再レビュー、その後の`//resume-all`(自動再開含む)を
何度繰り返しても、論理的に解決不可能な状態になっていました。

調査の結果、タスクキューへの割り当て自体は常に計画通りのファイル名で
行われており(実装結果を保存する`dest_path`は、設計担当の回答を都度
解析し直すのではなく、合意フェーズで確定した`tasks`のファイル名を
そのまま使います)、Yoriai側の処理でファイル名が取り違えられている
わけではないことを確認しました。原因は、設計担当(LLM)が1回の応答の
中で、計画の見出し行(実際のファイル名)と、他のファイルの説明文中の
言及(架空のファイル名)とで、矛盾した名前を使ってしまうことでした。

- **予防**: 合意フェーズのプロンプトに、「あるファイルの説明の中で他の
  ファイルに言及する場合、そのファイル名は実際にこの計画で挙げている
  名前と一字一句完全に一致させること」という指示を追加しました(既存の
  「同じ関数には同じ名前を使う」という指示の、ファイル名版です)。
- **検出**: 合意フェーズの直後(実装・レビューを始める前の、最も早い
  タイミング)に、各ファイルの説明文を機械的にスキャンし、「このプロジェクト
  が実際に使っている拡張子を持ちながら、どのタスクのファイル名とも
  一致しない」トークンが無いかを確認します。見つかった場合は、処理を
  中断せずに次のように警告を表示します(設計担当の記述ミスの可能性を
  示すだけで、実装自体は続行します。外部CDNのファイル名への言及等、
  誤検出の可能性もゼロではないためです)。

  ```
  [⚠️ index.html の説明文が、計画に無いファイル「script.js」に言及しています。
  設計担当の記述ミスの可能性があります(実装予定のファイル一覧: index.html, style.css, editor.js, preview.js)]
  ```

- **保険**: レビュー担当がread_fileツールで存在しないファイルを確認
  しようとした場合、それが「まだ実装されていないだけの、計画通りの
  ファイル」なのか、「そもそも計画に無い架空のファイル名」なのかを
  区別して報告するようにしました。後者の場合は、次のように計画に
  実在するファイル一覧を提示し、レビュー担当自身が実在するどのファイルを
  参照すべきだったのか気づける可能性を高めます。

  ```
  {"filename": "script.js", "exists": false, "message": "'script.js' は実装計画(PROGRESS.mdのモジュール分割案)に含まれていないファイル名です。新規に作成するつもりであればwrite_fileを使ってください。そうでなければ、計画の記述ミスの可能性があります。計画に実在するファイル: editor.js, index.html, preview.js, style.css"}
  ```

### 生成物の保存先(`projects/<プロジェクト名>/`)

協業モード(`//agree`・自動判定)の生成物は、Yoriai本体(`yoriai.py`・`config.py`等)と同じディレクトリには
保存されません。`--dir`で指定したディレクトリ(既定値はカレント
ディレクトリ)の配下に`projects/<プロジェクト名>/`というサブディレクトリを
作り、そこにファイル一式をまとめて保存します。

```
Yoriai> //agree ToDoリストのCLIツールを作って
[🧭 合意フェーズ開始: まず MacStudio (モデル: qwen2.5-coder-32b) にモジュール分割案とインターフェース設計を相談しています...]
...
[📁 生成物の保存先: ./projects/260825-todo-cli]
[🔨 実装フェーズ開始: 合意した計画に基づき、2件のファイルを異なるメンバーに並行実装させます]
...
[💾 ./projects/260825-todo-cli/storage.py に保存しました (担当: MacStudio)]
[💾 ./projects/260825-todo-cli/cli.py に保存しました (担当: junnoMac-mini)]
...
[✅ レビュー完了 (保存先: ./projects/260825-todo-cli)]
```

- **プロジェクト名の生成**: 依頼文に含まれるASCII英数字のまとまり
  (`ToDo`・`CLI`のように、日本語の依頼文に埋め込まれた英語表現)を
  最大4つまで拾い、ハイフンでつないだ簡易的な名前にします
  (例:「ToDoリストのCLIツールを作って」→`todo-cli`)。英語表現が
  全く含まれない依頼文の場合は`project`という既定名にフォールバック
  します。
- **日付プレフィックス**: 実際にディレクトリを作る際は、この名前の
  先頭に作成時点の日付(`YYMMDD`形式)を付けます(例: `260825-todo-cli`)。
  プロジェクトが増えても、いつ作られたものかが一覧(`ls projects/`)から
  一目で分かるようにするためです。
- **既存プロジェクトとの衝突回避**: 同名の`projects/<日付>-<名前>/`が
  既に存在する場合、既存の生成物を上書きしないよう`<日付>-<名前>-2`・
  `<日付>-<名前>-3`のように連番を振ります(同じ日に同じ依頼文で複数回
  作った場合などに発生します)。
- 実装フェーズ・レビューフェーズのログには、実際に保存されたファイルの
  フルパス(`[💾 ...に保存しました]`)や、最終的な保存先ディレクトリ
  (`[✅ レビュー完了 (保存先: ...)]`)が常に表示されます。
- `.gitignore`に`projects/`を追加してあるため、生成物がYoriai本体の
  Git管理下に誤って混ざることはありません。
- この仕組みは協業モード(`//agree`・自動判定)専用です。`//parallel`
  (ファイル名・依頼内容を手動で指定するコマンド)は、従来通り`--dir`で
  指定したディレクトリ直下にそのまま保存します(ユーザー自身がファイル名を
  完全に把握・指定している前提のため)。

### バックグラウンド実行(処理中も次の依頼を入力できる)

協業モード(`//agree`・自動判定)・`//parallel`・`//resume-all`(後述)は、
入力ループをブロックしないバックグラウンドスレッドで処理されます。処理中も
引き続き次の依頼を入力でき、進行ログはそのまま画面に流れます(Claude Code
等のツールと同様の体験です)。

```
Yoriai> //agree ToDoリストのCLIツールを作って
[🧭 合意フェーズ開始: まず MacStudio (モデル: qwen2.5-coder-32b) にモジュール分割案とインターフェース設計を相談しています...]
Yoriai> 富士山の標高は?
[MacStudio に問い合わせています... (モデル: qwen2.5-14b)]
3776メートルです。
[📐 モジュール分割案がまとまりました(2ファイル): storage.py, cli.py]
...
[✅ 全タスク完了 (保存先: ./projects/todo-cli)]
Yoriai>
```

- 先に入力した`ToDoリストのCLIツールを作って`(協業モード)の処理が
  バックグラウンドで進んでいる間に、続けて`富士山の標高は?`という
  別の質問を入力・送信できています。単発質問の応答と、バックグラウンド
  で進行中の協業モードのログが同じ画面に混ざって表示されます。
- 既に実行中の処理がある状態でさらに`//agree`等を入力すると、
  「実行中の処理があるため、この依頼は完了後に順番にバックグラウンドで
  処理されます」という通知が表示されます。バックグラウンドジョブは
  1本のキューで順番に(FIFOで)処理されるため、複数の協業モードの
  依頼が同じ組織のメンバーを同時に取り合うことはありません。
- 単発質問・`//multi`(比較質問)はバックグラウンド化の対象外で、
  これまで通り同期的に(その場で完了を待ってから次の入力に戻る形で)
  実行されます。会話履歴を共有・追記する仕組みのため、非同期化すると
  発言の順序が壊れかねないための意図的な設計判断です(詳細は
  [DEVELOPMENT_LOG.md](./DEVELOPMENT_LOG.md)の「実装上の判断メモ」を参照)。
- `exit`・`quit`・Ctrl+D・Ctrl+C2回連続(非常口)による対話モードの
  終了は、バックグラウンドジョブの完了を待たずに行われます。処理の
  途中で終了しても、後述のPROGRESS.mdにより進行状況はディスク上に
  残るため、`//resume-all`で後から再開できます。

### 進行状況の永続化(`PROGRESS.md`)と未完了プロジェクトの再開(`//resume-all`)

協業モードは合意フェーズ→タスクキュー方式による実装・レビューと複数の
フェーズにまたがり、実機では数分単位の時間がかかることもあります。
途中でプロセスが終了した場合(対話モードを再起動した、非常口で強制
終了した等)に最初からやり直さずに済むよう、プロジェクトディレクトリ
(`projects/<プロジェクト名>/`)に`PROGRESS.md`を作成し、タスクの状態が
変わるたびに更新し続けます。read_fileツール(レビュー担当がディスク上の
ファイルを都度読み直す仕組み)と同じ「ディスク上の実際の状態を正として
扱う」という設計方針を踏襲しています。

```
$ cat projects/todo-cli/PROGRESS.md
# プロジェクト進行状況

## 元の依頼

ToDoリストのCLIツールを作って

## モジュール分割案

storage.py: ToDoの永続化(JSON保存)を担当
cli.py: コマンドライン操作を担当

## タスク状況

✅ storage.py の実装
✅ storage.py のレビュー
✅ cli.py の実装
⏳ cli.py のレビュー

## 自動再開の試行回数

1

## 直近のレビュー指摘

### cli.py

引数の扱いが計画と異なります。addサブコマンドの引数名を計画通りにしてください。
```

- **内容**: 元の依頼文・合意フェーズが確定したモジュール分割案(ファイルごとの
  役割)・タスクチェックリストの現在の状態・(未完了のファイルがあれば)
  直近のレビュー指摘、をまとめて記録します。
- 全タスクが完了すると、チェックリストの全項目が✅になった状態の
  PROGRESS.mdがそのまま残ります(削除はしません)。「直近のレビュー指摘」の
  節は、未解決の指摘が無くなれば消えます。

未完了のPROGRESS.mdを持つプロジェクトを全て探し出し、順番に完走させ続ける
専用モードが`//resume-all`です。

```
Yoriai> //resume-all
[🔁 巡回モード開始: 未完了のプロジェクトが2件見つかりました]
  - ./projects/todo-cli
  - ./projects/weather-cli
[🔁 ./projects/todo-cli を再開します: 未完了1件 (cli.py)]
...
[🔁 ./projects/weather-cli を再開します: 未完了2件 (api.py, cli.py)]
...
[✅ 全プロジェクトの未完了タスクが完了しました]
```

- **再開の粒度はファイル単位**です。実装は完了しているがレビューだけが
  未完了のファイルも、既存のタスクキュー方式にそのまま乗せて実装から
  やり直します(「レビューだけを再開する」という専用の経路はありません)。
  実装済みのコードが再度実装し直されるのは無駄になり得ますが、既存の
  タスクキュー方式・レビューフェーズをそのまま再利用できます。
- 複数の未完了プロジェクトは**1つずつ順番に**再開されます(プロジェクトを
  またいで並行実行すると、同じ組織のメンバーを複数のプロジェクトが
  同時に取り合うことになり複雑さが増すため)。
- `//resume-all`自体もバックグラウンドで処理されるため、巡回モードの
  実行中も引き続き次の依頼を入力できます。
- 依頼で例示された「[✅ 全プロジェクトの未完了タスクが完了しました]」という
  文言は、実際に全プロジェクトが完了した場合にのみ表示されます。組織への
  問い合わせに失敗した等でプロジェクトが未完了のまま残った場合は、
  「✅ 完了」を安易に名乗らず「[⚠️ 巡回モード終了: N件のプロジェクトが
  未完了のまま残っています]」と正直に報告します(タスクチェックリストの
  最終チェックと同じ方針です)。

#### 未完了で終わった協業モードの自動再開(有限の上限付き)

`//resume-all`はユーザーが手動で実行するコマンドですが、協業モードの
処理が未完了のまま終わった直後には、ユーザーの確認を挟まず自動的に
もう一度そのプロジェクトを再開します(既存の`//resume-all`と同じ
ロジック、`_resume_project`をそのまま使います)。

```
Yoriai> //agree ToDoリストのCLIツールを作って
[🧭 合意フェーズ開始: まず MacStudio (モデル: qwen2.5-coder-32b) にモジュール分割案とインターフェース設計を相談しています...]
...
[⚠️ 未完了のタスクが残っています: cli.py のレビュー]
[🔁 ./projects/todo-cli: 未完了のタスクが残っているため、自動的に再開します(試行 1/3)]
[🔁 ./projects/todo-cli を再開します: 未完了1件 (cli.py)]
...
[✅ 全タスク完了 (保存先: ./projects/todo-cli)]
```

- **上限は3回**です。3回自動再開を試みても未完了のタスクが残っている
  場合は、それ以上の自動再開は行わず、次のように明示的に報告して
  停止します。

  ```
  [🔁 ./projects/todo-cli: 未完了のタスクが残っているため、自動的に再開します(試行 3/3)]
  ...
  [⛔ ./projects/todo-cli: 自動再開の上限(3回)に達しました。これ以上の自動再開は行いません。人間の確認が必要です]
  ```

- **既存の暴走防止の仕組み(1ファイルあたりレビュー往復は最大2回まで)は
  そのまま維持**されています。今回の上限(3回)は、それとは独立した
  プロジェクト単位での「外側の歯止め」です。
- 試行回数はPROGRESS.mdの「自動再開の試行回数」セクションに記録され、
  対話モードのプロセスを再起動しても引き継がれます(ディスク上の実際の
  状態を正として扱う設計方針を踏襲)。
- **手動`//resume-all`はこのカウンタと無関係**です。自動再開の上限に
  達したプロジェクトであっても、`//resume-all`を手動で実行すれば
  これまで通り何度でも再開を試みることができます(上限は「自動で
  勝手に回る場合」にのみ適用されます)。
- 自動再開も協業モードの処理の一部としてバックグラウンドで行われるため、
  自動再開中も引き続き次の依頼を入力できます。

### 実行モードの自動判定(コマンド不要化)

コマンドを付けずに話しかけるだけで、依頼文の内容からYoriai自身が適切な
実行モード(単発質問/比較/協業/既存プロジェクトの修正)を判定します。
既存の明示コマンド(`//agree`・`//multi`・`//fix`等)は、自動判定を
上書きしたい場合の手動指定として引き続き使えます。

```
Yoriai> 富士山の標高は?
[判断: 単発の質問と判断しました]
[MacStudio に問い合わせています... (モデル: qwen2.5-14b)]
3776メートルです。

Yoriai> このライブラリについて意見を聞かせて
[判断: 複数の意見を求めていると判断し、複数メンバーに問い合わせます]
[📡 ...台に同時問い合わせしています: ...]
...

Yoriai> ToDoリストのCLIツールを作って
[判断: 制作依頼と判断し、事前すり合わせを行います]
[🧭 対話プロトコルによる合意フェーズ開始: ...]
...
```

- 判定は`_classify_execution_mode`によるキーワードベースの単純な判定です。
  「作って」「作成して」「開発して」等の制作系キーワードがあれば協業モード、
  「意見を聞かせて」「比較して」等の比較系キーワードがあれば比較モード、
  完成済みプロジェクトがあり「直して」等の修正系キーワードがあれば修正
  モード、どれにも当てはまらなければ単発モードになります。
- 判定根拠は、既存のメンバー選定理由の表示と同じスタイルで
  `[判断: ...]`として画面に一言表示されます。

**対話プロトコルが一時停止した直後の発言は、自動判定を経由しません。**
以前(自動判定そのものを一度廃止していた時期)は、対話プロトコルが人間の
確認を求めて一時停止した直後の感想・追加指示のような、直前のやり取りへの
純粋な"続き"の発言までゼロから判定し直され、無関係な新規のやり取りとして
扱われてしまう問題がありました。会話履歴の一本化(後述)により、一時停止の
報告そのものが会話履歴に記録されるようになったため、直前の履歴が一時停止の
報告かどうかを見て自動判定をスキップできるようになり、この問題を回避しつつ
自動判定を復活させています。

`//agree`の合意フェーズ(対話プロトコル)が一時停止した直後の発言は、単なる
チャットの続きではなく、**合意フェーズそのものを続きから再開する回答**として
扱われます。人間の回答を踏まえて対話プロトコルが合意に達すれば、それまでの
議事録・要約を引き継いだままそのままタスク分解・実装フェーズへ進みます
(合意に達しなくても、設計担当1名が人間の回答を踏まえて計画を単独で確定し、
実装フェーズへ進むため、一時停止を何度も繰り返すことはありません)。それ以外の
一時停止(`//plan-only`の一時停止等)では、これまで通り単なる会話の続きとして
扱われます。

```
Yoriai> //agree ToDoリストのCLIツールを作って
[🧭 対話プロトコルによる合意フェーズ開始: ...]
...
[🙋 対話プロトコル: 合意に至らず、人間の確認が必要です]
[👤 続行するか終了するかは人間の判断です。内容を確認のうえ、必要であれば依頼文を調整して再度お試しください]

Yoriai> うん、それでいいから進めて
[💬 対話プロトコルの一時停止直後の発言のため、合意フェーズを続きから再開します]
[🧭 対話プロトコルを再開します: 人間の回答を踏まえてラウンド2から続けます...]
...
[🧭 対話プロトコルで合意した計画(そのまま表示)]
...
[📐 モジュール分割案がまとまりました(2ファイル): storage.py, cli.py]
...
```

- コマンド無しの発言と、単発質問・`//multi`(比較質問)は、`--chat`の
  1回の起動中は常に同じ会話履歴を共有します(詳しくは後述の「会話履歴の
  一本化と会話ログの保存」を参照)。
- `//plan-only`・`//parallel`・`//resume-all`は、明示的にコマンドを
  付けたときにのみ実行されます(制作系・比較系キーワードによる自動判定の
  対象は協業モード・比較モード・修正モードの3つで、これらは含みません)。
- `//fix`セッション中は、コマンド無しの発言が制作系・比較系キーワードを
  含んでいても自動判定にはかけず、常にそのセッションの続き(対象
  プロジェクトへの継続的な修正依頼)として扱います(セッションを終えるには
  「終了」と送るか、明示的に別のコマンドを使ってください)。

### 既存プロジェクトへの修正依頼(`//fix`)

これまでの協業モードは「新規のプロジェクトをゼロから作る」ことしかできず、
既に完成したプロジェクトに対して「ここを直して」という修正依頼を送る手段が
ありませんでした。Claude CodeにおけるRead/Glob/Grep/Editのような、既存
ファイルに対する検索・部分修正の仕組みをYoriaiにも導入しています。

```
Yoriai> //fix ファイル名をutils.pyからhelpers.pyに変更して、それに合わせてimportも直して、テストがあれば実行して確認して
[🔧 対象プロジェクトを特定しました: ./projects/todo-cli-storage-py-2]
[🔧 junnoMac-mini (モデル: qwen2.5-coder-14b) に修正を依頼しています...]
[📖 cli.py を読みに行っています...]
[📦 utils.py を helpers.py に変更しています...]
[✏️ cli.py を書き込んでいます...]
[🧪 pytest を実行しています...]
utils.pyをhelpers.pyにリネームし、cli.pyのimportを修正してテストを実行しました。
[✅ 修正が完了しました (プロジェクト: ./projects/todo-cli-storage-py-2, 変更したファイル: helpers.py, cli.py)]
```

- `//fix <修正依頼>`と明示的にコマンドを付けて呼び出せるほか、完成済みの
  プロジェクトが1件以上ある状態で「直して」等の修正系キーワードを含む
  コマンド無しの発言を送った場合も、自動判定により同じ経路で実行されます
  (詳しくは前述の「実行モードの自動判定」を参照)。プロジェクト名を
  省略した場合、対象プロジェクトの特定は次の「プロジェクトの特定」で
  説明する仕組みが自動で行います。
- **プロジェクトの特定**は、依頼文と各プロジェクトのPROGRESS.md(元の依頼・
  モジュール分割案)を文字バイグラム(2文字の連なり)の重なりで照合する
  単純な方式です。複数の候補が拮抗した場合や、十分な一致が見つからない
  場合は、その場で推測せず次のように確認を求めます。

  ```
  Yoriai> //fix ID生成のロジックにバグがあるので直して
  [❓ 複数のプロジェクトが候補に挙がりました: todo-cli-1, todo-cli-2]
  どのプロジェクトのことでしょうか? //fix todo-cli-1: ID生成のロジックに
  バグがあるので直して のように、プロジェクト名を付けて教えてください。
  ```

  `//fix <プロジェクト名>: <修正依頼>`のようにプロジェクト名を先頭に付けて
  明示指定すると、この自動判定を経由せず直接そのプロジェクトを対象にできます。
- 対象にできるのは**タスクチェックリストが全て完了している(✅)プロジェクト
  のみ**です。未完了のプロジェクトが該当した場合は、先に`//resume-all`で
  完了させるよう案内し、修正は行いません。
- **修正の実行は、担当メンバーが専用のツール一式を使って自律的に行います**
  (Claude CodeのBashツールのような「任意のシェルコマンドを実行できる」形は
  避け、用途を絞った専用ツールのみを提供しています)。

  | ツール | できること |
  | --- | --- |
  | `read_file` | プロジェクト内の既存ファイルの中身を読む |
  | `list_dir` | プロジェクト内のファイル一覧を確認する |
  | `write_file` | ファイルを新規作成・上書きする |
  | `move_file` | ファイル名を変更(移動)する |
  | `make_directory` | サブディレクトリを作成する |
  | `delete_file` | 不要なファイルを削除する |
  | `run_command` | ファイルの検証(動作確認)に使う、検証専用のコマンド実行ツール(下記) |

  リネーム→import修正→動作確認のように、複数のツールを何度でも
  組み合わせて使えるため、1ファイルの書き換えでは表現できない修正依頼にも
  対応できます。Yoriai側で「どのファイルを直すべきか」を先読みして決め打ち
  することはせず、担当メンバー自身に実際のファイルを確認させながら
  判断してもらいます。
- **すべての操作は対象プロジェクトディレクトリの内側だけに限定**されます
  (依頼の安全要件)。ファイル名はディレクトリ区切りを含まないフラットな
  名前のみが許可され、`../../etc/passwd`のようなパストラバーサル文字列や、
  Yoriai本体(`yoriai.py`)・他のプロジェクトディレクトリへの絶対パスは
  すべて拒否されます。`PROGRESS.md`自体もYoriaiが管理するファイルのため、
  これらのツールでは操作できません(直接の作成・上書き・削除はいずれも拒否)。
- **`run_command`は、拡張子ごとの決め打ちコマンドではなく、担当メンバーが
  検証に適したコマンドを自分で判断して自由に実行できる、検証専用のツール
  です**(Claude CodeのBashツールのような無制限の実行権限とは異なります)。
  以前は`.py`→`python3`、`.c`→`gcc`のように対応済みの組み合わせしか
  実行できず、対応していない状況(HTML/CSS等)ではモデルが見当違いの
  コマンドを何度も試してツール呼び出し回数の上限を無駄にする実機の
  不具合が繰り返し報告されていたため、コマンド文字列を自由に指定できる
  代わりに、実行前に機械的なフィルタを必ず通す設計に置き換えました。
  拒否される主な操作:
  - ネットワークアクセス(`curl`・`wget`・`ssh`・`git`等)
  - ファイルの削除・移動・上書き(`rm`・`mv`・`cp`等。これらは
    `write_file`・`move_file`・`delete_file`を使うべき操作のため)
  - 権限昇格(`sudo`等)・シェル自体の起動(`bash -c`等)
  - `env`・`timeout`・`xargs`のような、他のコマンドを間接的に起動できる
    「ラッパー」経由での上記の迂回(コマンド文字列内の全トークンを
    チェックすることである程度防ぎます)
  - プロジェクトディレクトリの外を指すパス(絶対パス・`..`を含む相対パス)
  - `python3 -c`・`node -e`のような、インタプリタのインラインコード
    実行フラグ(`gcc -c`のような無関係な同名フラグは影響を受けません)
  - `;`・`|`・`&`・バッククォート・`$()`・リダイレクト(`<`/`>`)のような
    シェル構文(シェルは経由せず引数リストのまま渡すため、そもそも解釈
    されませんが、念のため文字列レベルでも拒否しています)

  これはホワイトリスト(許可リスト)ではなくブロックリスト(拒否リスト)
  方式のため、原理的に「絶対安全」を保証するものではないことに注意して
  ください。あくまで「検証・確認」の範囲内での柔軟性向上が目的です。
  実行時間は10秒、出力は4000文字までに制限され、超えた場合はそれぞれ
  強制終了・切り詰めが行われます(`yes`のように出力が止まらない
  コマンドでも、メモリを圧迫しないよう読み取り量にも別途上限があります)。
- **`check_html <HTMLファイル名>`は、実機にPlaywright(ヘッドレスブラウザ
  操作ツール)がインストールされている場合のみ`run_command`経由で使えます**。
  指定したHTMLファイルをヘッドレスブラウザで実際に開き、コンソールに
  出力されたエラー(`console.error`・未捕捉の例外)の有無を確認します。
  `id`名の不一致のようなJavaScriptの実行時エラー(構文としては正しいため
  `node --check`では検出できない)を機械的に検出できます。Playwrightが
  インストールされていない環境では、gcc・nodeが無い場合と同じく
  エラー扱いにはせずスキップされます(YoriaiがPlaywrightを自動で
  インストールすることはありません)。
- **ファイルの削除は、実行前にPROGRESS.mdへ記録し、ログにも明確に表示して
  から行います**(取り消せない操作のため)。
- 修正セッションが終わると、プロジェクト内の全`.py`ファイルに機械的な構文
  チェックが行われます(`write_file`の呼び出し直後にもその場で構文チェック
  結果がフィードバックされ、担当メンバー自身が気づいて直す機会もあります)。
  構文エラーが残っている場合は、ファイルへの反映自体は行われたうえで
  次のように警告が表示されます。

  ```
  [⚠️ 修正は保存されましたが、構文エラーが残っているファイルがあります: utils.py]
  ```

- **「修正が完了しました」という報告は、実際にファイルへの書き込みが
  確認できた場合にのみ表示されます**。以前は、モデルが問い合わせに応答
  さえすれば(たとえ`write_file`等のツールを一度も呼ばなかった、または
  呼んだが失敗した場合でも)無条件に「完了しました」と表示し、PROGRESS.md
  にも更新履歴を記録してしまう不具合がありました。現在は`write_file`・
  `move_file`・`delete_file`のいずれかが実際に成功したことを確認できた
  場合のみ完了として扱います。
- **モデルが「修正しました」と説明文だけを返し、実際にはツールを一度も
  呼んでいない場合、1回だけ実際にツールを呼ぶよう促して再試行します**
  (実機で、モデルが行動の説明だけをして実際には何もしないケースが
  報告されたための対応)。

  ```
  [⚠️ 説明文だけでツールが実際には呼ばれていないため、実行するよう促して再試行しています...]
  ```

  この再試行で実際にファイルが変更されれば、通常通り「完了しました」と
  報告されます。促しても改善しなければ(無制限には促し続けません)、
  次のように正直に報告し、PROGRESS.mdへの記録も行いません。

  ```
  [ℹ️ 修正が実行されませんでした(ファイルへの書き込み・変更が一度も確認できませんでした)。依頼内容を具体的にして再度お試しください]
  ```

  ツール呼び出しの往復回数の上限に達した等でセッションが途中終了した
  場合も、それまでに実際に成功した変更だけは失われず反映されます。この
  場合は「完了しました」ではなく、次のように途中終了である旨と、実際に
  変更されたファイルの両方を正直に報告します。

  ```
  [⚠️ 修正セッションが最後まで正常に完了しませんでした(ツール呼び出しの往復回数が上限(50回)に達しました)。ただし一部のファイルは実際に変更されています: utils.py]
  ```

- 修正が完了すると、対象プロジェクトのPROGRESS.mdに更新履歴が追記されます。
  実際に変更されたファイル名も含まれるため、更新履歴と実際の変更内容が
  食い違うことはありません。

  ```
  $ cat projects/todo-cli-storage-py-2/PROGRESS.md
  ...
  ## 更新履歴

  - 2026-08-21: legacy.pyを削除して
  - 2026-08-21: ファイル名をutils.pyからhelpers.pyに変更して、それに合わせてimportも直して、テストがあれば実行して確認して [変更ファイル: helpers.py, cli.py]
  ```

  (1行目はdelete_fileツールが削除の直前に記録したもの、2行目は依頼全体の
  完了時にまとめて追記されたものです。)この更新履歴はPROGRESS.md自体と
  同様、プロセスを再起動しても・`//resume-all`で他のタスクを再開しても
  失われません。

### トークン使用量に関する調査と削減(read_fileの内容切り詰め)

複雑で大きな依頼(HTML/CSSの学習サイト、プレビュー連動機能を含む、等)を
送ったところ、シンプルなタスク(ToDoリストなど)と比べてLM Studio側の
トークン使用量が明らかに膨らむという報告を受けて調査を行いました。

**調査結果**:

- **「1回目のレビュー→修正依頼→修正後の再レビュー」の間で、会話全体が
  そのまま持ち越されることはありません。** これら3つの段階(および
  実装依頼)はそれぞれ独立した`/chat`呼び出しで、`[{"role": "user",
  "content": <その段階専用に組み立てたプロンプト>}]`という新しい会話
  として毎回始まります。前の段階でread_fileツールを使って読んだ
  ファイルの中身が、次の段階に引き継がれることはありません。
- 一方、**1回のレビュー(またはfixツール一式によるセッション)の「中」
  では**、read_file等のツール呼び出し結果は会話履歴に累積されます。
  `/chat`は毎回それまでのやり取り全体を送信し直すステートレスな設計
  のため、複数回ツールを呼ぶほど、そのラウンドの送信量が積み上がって
  いきます(read_fileはレビュー1回につき最大3回、修正ツール一式は
  1セッションにつき最大50回まで)。これは正しい判断のために必要な
  情報であり、単純に「消せば良い」ものではありませんが、**読み込む
  ファイル自体が大きい場合(HTML/CSSの学習サイトのような、1ファイルが
  数万文字に達するケース)には、この積み上がりが大きく効いてきます**。
- 加えて、合意フェーズで確定したモジュール分割案(`full_plan`)は、
  実装・レビュー・修正のそれぞれのプロンプトに**毎回そのまま埋め込まれます**
  (これも「会話の持ち越し」ではなく、各段階が独立して埋め込み直して
  いるものです)。分割案そのものは通常「ファイル名: 概要」程度の短い
  行の集まりであるため、今回確認した範囲では主要因ではありませんでした。

**実施した対策**: read_fileツールが返すファイルの中身と、レビュー担当
自身の担当ファイル(参考としてプロンプトに直接埋め込まれる分)に、
`_FILE_CONTENT_TRUNCATE_CHARS`(既定12,000文字)の上限を設けました。
上限を超える場合は先頭からその文字数までに切り詰め、切り詰めたことを
明示するメッセージを添えます。

```json
{"filename": "index.html", "exists": true, "content": "...(先頭12,000文字)", "truncated": true, "message": "ファイルサイズが大きいため、先頭12000文字のみを返しています(トークン使用量を抑えるための制限です)。"}
```

- **レビュー対象そのもの(これから合否を判断してもらうファイル)は
  切り詰めません。** 切り詰めた不完全な内容を根拠に合否を判断させる
  のは、トークン削減と引き換えにレビューの意味を失わせてしまうため
  本末転倒だと判断しました。切り詰めの対象は、あくまで「参考として
  見せるだけ」の補助的な情報(read_fileで確認する他ファイル、レビュー
  担当自身の担当ファイル)に限定しています。
- 内容を完全に削除・省略するのではなく「上限付きで返す」設計にしたのは、
  情報を丸ごと失わせないため(判断材料が完全に消えるより、先頭部分だけ
  でも見える方が有用な場合が多いと判断しました)。読みたい範囲を絞り
  込む機能(read_fileへのオフセット指定等)までは今回のスコープ外とし、
  まず無条件の上限による歯止めのみを入れています。

### 言語非依存の設計への刷新

これまでのYoriaiは、構文チェック(`ast.parse`)・テスト実行
(`python3`/`pytest`)・合意フェーズのプロンプト例(`storage.py`/`cli.py`)が
暗黙的にPythonを前提にした作りになっており、「HTML/CSSの学習サイトを
作って」のような非Python依頼を送ると、設計担当がPython風のファイル分割に
引きずられてしまう不具合がありました。今後「〇〇語で作って」と言語を
指定した場合にも、コードを個別に直さずに対応できるよう見直しています。

```
Yoriai> //agree C言語で、簡単な電卓プログラムを作って
[🧭 合意フェーズ開始: まず MacStudio (モデル: qwen2.5-coder-32b) に
モジュール分割案とインターフェース設計を相談しています...]
...
[📐 モジュール分割案がまとまりました(1ファイル): calc.c]
  - calc.c: 四則演算を行うmain関数を実装する
[🗂️ 使用言語と判断しました: C]
...
```

```
$ cat projects/calc/PROGRESS.md
# プロジェクト進行状況

## 元の依頼

C言語で、簡単な電卓プログラムを作って

## 使用言語

C

## モジュール分割案

calc.c: 四則演算を行うmain関数を実装する
...
```

- **言語の判定は2段階**です。(1)ユーザーが依頼文の中で言語・技術を明示した
  場合(「C言語で作って」「JavaScriptでゲームを作って」等)は、それを最優先で
  設計担当への指示に埋め込みます。明示が無い場合は、設計担当(LLM)自身に
  依頼内容から適した言語を判断してもらいます(「ToDoリストのCLIツールを
  作って」のような依頼はこれまで通りPythonになりますが、Yoriai側で言語を
  決め打ちしているわけではありません)。(2)PROGRESS.mdに記録される「使用
  言語」は、依頼文からの推測ではなく、**実際に設計担当が提案したファイルの
  拡張子から逆算した値**です。依頼と実際の生成物が食い違うリスクを避け、
  常に「実際のファイル」を正とするためです。
- **構文チェックはファイルの拡張子に応じて自動的に切り替わります**
  (プロジェクト全体の設定ではなく、ファイル単位の判定です。1つの
  プロジェクトにHTML/CSS/JavaScriptのように複数の拡張子が混在することが
  普通にあるためです)。

  | 拡張子 | 挙動 |
  | --- | --- |
  | `.py` | 従来通り`ast.parse`で構文チェック |
  | `.html` | マークアップ自体の構文チェックはスキップ(標準ライブラリだけでは信頼できるチェック手段が無いため)。ただし`<script>`タグに直接書かれたインラインJavaScriptは、外部ファイル参照(`src`属性付き)やJavaScript以外(`type="application/json"`等)を除いて`node --check`でチェックする(実機に`node`が無ければスキップ) |
  | `.css` | 構文チェックをスキップ(標準ライブラリだけでは信頼できるチェック手段が無いため) |
  | `.js` | `node --check`(実機に`node`が無ければスキップ) |
  | `.c` | `gcc -fsyntax-only`(実機に`gcc`/`cc`が無ければスキップ) |
  | それ以外 | 「この言語の構文チェックには対応していません」と明示してスキップ |

  スキップは失敗(エラー)としては扱われません。構文エラーが実際に見つかった
  場合のみ、これまで通りレビュー往復の対象になります。
- **動作確認は`run_command`ツールで行います**(以前この節にあった、
  言語ごとに拡張されたホワイトリスト形式の`run_test`は、より柔軟な
  検証専用ツール`run_command`に置き換わりました。詳細は前述の
  「既存プロジェクトへの修正」の節を参照してください)。C言語のように
  「コンパイル」と「実行」が別コマンドの場合、シェルの`&&`のような連結は
  使わず、担当メンバーが`run_command`を2回(コンパイル→実行)呼び出す
  形は変わっていません。
- **`//fix`での修正時も、対象プロジェクトの使用言語がプロンプトに
  含まれます**。担当メンバーがどの言語・拡張子で作業すべきかを常に
  意識できるようにするためです。この機能追加より前に作られた
  PROGRESS.md(「使用言語」の記録が無い)を対象にした場合は、モジュール
  分割案のファイル拡張子からその場で言語を補完します(`//resume-all`で
  古いプロジェクトを再開した場合も同様です)。
- 今回作られてしまった`html-css-html-css`プロジェクトのような、言語判定を
  誤った既存の生成物への対処は、依頼の通りスコープに含めていません。今後
  新しく作られる・再開されるプロジェクトから正しく機能します。

### モデルがツール呼び出しに対応していない場合の自動フォールバック

問い合わせ先に選ばれたメンバーのモデルが、ウェブ検索などのツール呼び出し
(Function Calling)にうまく対応していない場合、Yoriaiは自動的に検知して
ツール無しの通常のチャットとして同じメンバーへ再試行します。特別な操作は
不要で、対話モード側では次のように表示されます。

```
Yoriai> このPythonの関数のバグを直して: def add(a, b): return a - b
[コーディング系の質問と判断し、コーディング系モデルを優先: junnoMac-mini に問い合わせています... (モデル: qwen3-coder-30b)]

[⚠️ このモデルはツール呼び出しの構造化出力に対応していないようです。ツールなしで再試行しています...]
この関数は `a - b` を返していますが、関数名が `add` なので、足し算を行うべきです。
...
```

- 検知するのは主に2パターンです。(1)モデルがツール呼び出しの記法(`<tool_call>`等)を
  そのまま回答本文に出力してしまうケース、(2)モデルへの問い合わせ自体がツール付きだと
  400/422エラーで拒否されるケース。どちらも同じ`[⚠️ ...]`という案内が表示され、
  自動的に同じメンバー・同じモデルへツール無しで再試行されます。
- 「モデルのロード失敗(メモリ不足)」のように、ツールとは無関係な理由で400/422が
  返ってきた場合は、この自動フォールバックの対象にはなりません(再試行しても
  解決しないため)。その場合は通常のエラーとして扱われ、次に優先順位が高い
  メンバーへのフォールバックが行われます。
- この一連の判定・再試行はキッチン(常駐エージェント)側で完結するため、対話モード
  (フロント)は特に意識する必要はありません。

### MLX-LMバックエンド対応

Ollama・LM Studioに加えて、MLX-LM(`python -m mlx_lm.server`、Apple Silicon上で
動く推論エンジン)にも対応しています。特別な設定は不要で、MLX-LMのサーバーが
既定ポート(8080)で起動していれば自動的に検出されます。

> **現在の状況**: MLX-LMサーバー自体が正常に応答することはcurlによる直接
> 検証で確認済みです。また、実機検証の過程でメンバー選定ロジックの不具合
> (LM Studioと同時に動かしている場合にMLX-LM側が選ばれない)が見つかり、
> 修正済みです。詳しくは「フェーズ6-3の追加調査」を参照してください。ただし、
> 修正後に`//multi`・通常の対話モード双方でMLX-LM側が正しく選ばれることの
> 実機での最終確認はまだ行われていません。

- `--status`や対話モードの選定ログで表示されるモデル一覧に、MLX-LMで動いている
  モデルも自動的に含まれます。
- `--status`の各メンバーの表示に「利用可能なバックエンド」という行が追加され、
  そのメンバーで実際に動いているバックエンド(`ollama`/`lmstudio`/`mlx_lm`のうち
  該当するもの)が一覧表示されます。
- チャットの問い合わせ先バックエンドは、Ollama→MLX-LM→LM Studio(デフォルト)の
  順でモデル名の一致を見て自動的に振り分けられます。

### 対話プロトコル(複数ノードによる合意形成、フェーズ7)

これまでの`//agree`は、計画フェーズで1〜2往復程度のやり取りをしただけで
そのまま実装フェーズに進んでしまい、「最初に思いついた案がそのまま最後まで
固定される」「自己反証のループが実質ゼロ」という問題がありました。これを
解消するため、複数のノード(LLM)が役割を持って議論し、合意形成していく
**対話プロトコル**を実装しました。特定のフェーズ専用の機能ではなく、寄合
全体で使い回せる共通基盤として実装しており、計画フェーズ(`//agree`)・
修正フェーズ(`//fix`)・レビューフェーズ・新設の`//plan-only`から共通で
呼び出されます。

#### 役割の割り振り

議題ごとに、組織内の候補(得意分野・空きメモリで優先順位付けされた並び)
から、動的に3つの役割を割り振ります。

- **提案役**: 具体的な実装案・修正方針案を出す
- **反論役**: あえて穴やリスクを探し、批判的に検討する
- **統合役**: 複数の意見を俯瞰し、合意できたかどうかを判定してまとめる

候補が3台に満たない場合は同じノードが複数の役割を兼務します(2台なら
2台目が反論役・統合役を兼務、1台なら1台がすべての役割を兼務する自己対話に
なります。組織に1台しかいない場合でも対話プロトコル自体は動作します)。
各ノードには自己紹介カードの`device_name`をそのまま使った発言者ラベル
(「MacStudioさん」「junnoMac-miniさん」)が付き、議事録が人間にも読みやすく
なっています。役割割り振りの手がかりとして、自己紹介カードに`得意分野`
(`specialties`: `coding`/`general`の簡易な二値、既存のコーディング系モデル
判定を流用)を追加しました。

```
[🧭 対話プロトコルによる合意フェーズ開始: MacStudioさんを中心に、モジュール分割案とインターフェース設計について議論します...]
[💬 MacStudioさん(提案役・ラウンド1)] storage.py: add_todo(text: str) -> int を実装する...
[💬 junnoMac-miniさん(反論役・ラウンド1)] 並行アクセス時の扱いが曖昧です。評価: 要修正
[💬 junnoMac-miniさん(統合役・ラウンド1)] 判定: 継続
[💬 MacStudioさん(提案役・ラウンド2)] ロックファイルによる排他制御を追加しました...
[💬 junnoMac-miniさん(反論役・ラウンド2)] 問題なさそうです。評価: 合意
[💬 junnoMac-miniさん(統合役・ラウンド2)] 判定: 合意

最終合意内容:
storage.py: add_todo(text: str) -> int を実装する(ロックファイルによる排他制御あり)...
[🤝 対話プロトコル: 6件の発言を経て合意に達しました]
```

#### ラウンド数とセーフティリミット

ラウンド数は固定せず、統合役が「判定: 合意」と判断し(かつ反論役も
「評価: 合意」と答え)、既定2ラウンド以上を経ている場合に終了します。
最初のラウンドで両者が合意と答えても、2ラウンド目まで議論させることで
「最初の思いつきがそのまま固定される」ことを防ぎます。

暴走防止のため、参加している全ノードの発言回数の合計が**50回**を超えた
時点で強制的に一時停止します(1つの議題についての対話1回あたりで数え、
寄合全体を通しての累積ではありません)。

#### 人間へのエスカレーション

対話中、AIノード側(反論役・統合役)から能動的に人間へ問いかけられます。
反論役が「評価: 情報不足」(議論を重ねてもアイデアが出ない)と判断した場合、
または統合役が「判定: 人間に確認」と判断した場合、既定のラウンド数までに
合意できなかった場合のいずれでも、その時点までの議事録全文と要約を表示して
人間の判断を仰ぎ、**次のフェーズには自動的に進みません**。最終的な
「これでゴー」の判断は必ず人間が行うという方針に基づき、AIノード側だけで
最終決定して実装フェーズ等に進むことはしません。

```
[🙋 対話プロトコル: 合意に至らず、人間の確認が必要です]
議論を重ねましたが、まだアイデアが不足しており合意に至りませんでした。アドバイスをください。
[👤 続行するか終了するかは人間の判断です。内容を確認のうえ、必要であれば依頼文を調整して再度お試しください]
```

#### 議事録と要約の永続化

議事録(逐語ログ、誰が・どの役割で・何を発言したか)と要約(大まかな結論)を
必ずセットで、`PROGRESS.md`と同じプロジェクトディレクトリに別々のファイルと
して保存します(`DIALOGUE_LOG_<用途>.md`・`DIALOGUE_SUMMARY_<用途>.md`。
`<用途>`は`design`(計画フェーズ)・`fix`(修正フェーズ)・`plan`
(`//plan-only`)のいずれか)。合意・不合意どちらの結果でも保存されるため、
後から「なぜこの結論になったのか」を議事録から遡れます。

```
$ cat projects/todo-cli/DIALOGUE_SUMMARY_design.md
# 対話サマリー: 制作依頼「ToDoリストのCLIツールを作って」のモジュール分割・インターフェース設計

## ステータス

合意

## 要約

6件の発言を経て合意に達しました。

storage.py: add_todo(text: str) -> int を実装する(ロックファイルによる排他制御あり)...
```

#### 各フェーズでの利用

- **計画フェーズ(`//agree`)**: 設計担当1台への
  1回きりの相談だった合意フェーズが、対話プロトコルによる複数ラウンドの
  議論に置き換わります。合意した最終合意内容は、既存の「ファイル名: 内容」
  形式のままタスクキュー方式の実装フェーズにそのまま引き継がれるため、
  以降の実装・レビュー・`PROGRESS.md`・`//resume-all`の仕組みは一切
  変わりません。
- **修正フェーズ(`//fix`)**: 依頼の規模判定(分割するかどうか)の前に、
  修正方針についての対話プロトコルによる事前合意を挟みます。合意した方針は
  依頼文に追記され、以降の規模判定・実装依頼にそのまま引き継がれます。
  バックエンドへの疎通自体ができない場合(対話が一度も実のある応答を
  得られなかった場合)は、対話の不調を理由に修正を止めず、これまで通り
  元の依頼文のまま安全側にフォールバックします。
- **レビューフェーズ(自己説明・再利用)**: タスクキュー方式による実装・
  レビューでは、本番のレビューの前に、実装担当(提案役)がレビュー担当
  (反論役・統合役を兼務)へ設計判断を短く説明し、レビュー担当がその場で
  疑問点をぶつける軽量な自己説明対話を行います。説明に詰まる・要領を得ない
  場合、その申し送り事項が本番のレビュープロンプトに引き継がれ、レビュー
  担当の最終判断(「問題なし」/「問題あり」)の材料になります。議事録・
  要約のファイルへの永続化は(ファイルごとに大量に増えてしまうのを避ける
  ため)行いません。
- **計画のみモード(`//plan-only`、新設)**: 成果物(コード等)を実際に
  作らず、対話プロトコルによる議論の結果としての計画書(要約+議事録)だけを
  出力して終了する、新設の単体コマンドです。既存の新規作成モード
  (`//agree`)・修正モード(`//fix`)とは独立しています。

  ```
  Yoriai> //plan-only 大規模な学習管理システムを作りたいが、まず方針を相談したい
  [🧭 計画のみモード開始: MacStudioさんを中心に、対話プロトコルで計画について議論します(成果物の実装は行いません)...]
  ...
  [🧭 対話プロトコルでまとまった計画(そのまま表示)]
  - 全体方針: まずコース登録・進捗記録の最小構成から始め、通知機能は後続フェーズに回す
  - 主要な作業項目: ...
  - 想定されるリスク: ...
  ```

  生成物の保存先は`projects/<日付>-<プロジェクト名>-plan/`で、`//agree`による
  実装プロジェクト(`projects/<日付>-<プロジェクト名>/`)とは別ディレクトリに
  分かれます(議事録・要約以外のファイルは一切生成されません)。

### 会話履歴の一本化と会話ログの保存

以前は、単発質問・`//multi`(比較質問)だけが会話履歴を共有・蓄積しており、
`//agree`・`//fix`・`//plan-only`・`//parallel`・`//resume-all`はそれぞれ
独立した1回きりのやり取りとして処理されていました。そのため、対話プロトコルが
「人間の確認が必要です」と一時停止した直後に感想や追加の指示を送っても、それが
全く無関係な新規の単発質問として扱われてしまい、直前まで何を話していたかを
メンバー側が一切踏まえられないという不具合が実機で報告されました。

```
[👤 続行するか終了するかは人間の判断です。内容を確認のうえ、必要であれば依頼文を調整して再度お試しください]
Yoriai> Macminiからの応答がないじゃん。ちゃんと会話に参加させてよ
```

- **会話履歴の一本化**: `--chat`の1回の起動中は、単発質問・`//multi`だけでなく
  `//agree`・`//fix`・`//plan-only`・`//parallel`・`//resume-all`のやり取りも
  すべて同じ会話履歴に積み上げられます。これにより、上記のように対話プロトコルが
  一時停止した直後に単発質問を送っても、直前のやり取りを踏まえた回答が期待できます。
  以前からあった「修正セッション」(`//fix`後に対象プロジェクトへの継続的な発言を
  受け付ける限定的な仕組み)とは異なり、コマンドの種類を問わず`--chat`が起動して
  いる間は常に会話の記録が保持・引き継がれます。
- **会話履歴への記録には上限があります**: バックグラウンドジョブ(`//agree`等)の
  出力は長大になりうるため、次にLLMへ送り直す会話履歴に載せる分だけ
  8,000文字の上限で切り詰められます(画面表示自体は切り詰めません。read_file
  ツールの`_FILE_CONTENT_TRUNCATE_CHARS`と同じ、トークン使用量対策の考え方です)。
- **会話ログのファイルへの保存**: `--chat`を起動するたびに、起動時刻を
  ファイル名に持つ会話ログ(`chat_logs/chat_<YYYYMMDD_HHMMSS>.md`)が作られ、
  すべてのやり取り(発言者・タイムスタンプ・内容)が逐次追記されます。
  対話モードのプロセスを終了するとメモリ上の会話履歴は破棄されますが、この
  ログファイルはディスク上に残るため、別のセッションでも過去の会話内容を
  見返すことができます(自動で読み込んで引き継ぐ機能は今回のスコープ外です)。
- `.gitignore`に`chat_logs/`を追加してあるため、会話ログがYoriai本体のGit管理下に
  誤って混ざることはありません。
