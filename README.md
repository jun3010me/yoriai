# yoriai
寄合システム

ローカルLLM対応デバイス(Mac mini, MacBook Pro, Mac Studioなど)が同一ネットワーク上で
自動的にお互いを発見し、各デバイスのスペックや利用可能なモデル情報を自律的に交換し合う
「組織」のようなエージェント群システムのプロトタイプです。

## 今回のスコープ

このプロトタイプは以下を実装しています。

1. **自己紹介カードの生成**: デバイス名、OS/チップ情報、総メモリ/空きメモリ、
   インストール済みモデル一覧、ロード済み(メモリに乗っている)モデル一覧をJSONにまとめます。
   ローカルLLMバックエンドはOllama・LM Studioの両方に対応しており、どちらか一方
   (または両方)が動いていれば自動的にモデル情報を反映します。
2. **mDNSによる自動発見と自己紹介カードの交換**: 同一ネットワーク上の他のYoriaiエージェントを
   `zeroconf` (mDNS/Bonjour) で自動発見し、HTTP経由で自己紹介カードを取得してログに表示します。
3. **トークンによる参加制御(フェーズ2)**: 同じ「トークン(組織の合言葉)」を持つエージェント同士だけが
   自己紹介カードを交換します。トークンは `--init` で新規発行、`--join=<トークン>` で既存の組織に参加できます。
4. **Tailscale経由での発見(フェーズ2.5)**: mDNSは同一LAN内向けの発見として維持しつつ、
   Tailscaleで接続されたリモートデバイスも `tailscale status --json` のピア一覧を使って
   別枠で発見できるようにしています。
5. **Linux対応 + 常駐化(フェーズ4)**: macOSに加えてLinux(Raspberry Pi 4を含むDebian系など)
   でも動作します。macOSはlaunchd、Linuxはsystemdによる常駐化スクリプトも用意しており、
   SSHセッションを切っても動き続け、クラッシュ時は自動再起動されます。
   `./scripts/setup.sh` で初回セットアップ(venv作成・依存関係インストール・
   トークン設定・常駐化登録)を、`./scripts/update.sh` で最新コードの取得・
   依存関係の更新・常駐化サービスの再起動を、それぞれ1コマンドでまとめて行えます。

タスクの割り振り、Ollama/LM Studioの自動インストール、モデル剪定などは**次フェーズ以降**の対象です。

## 動作環境

- macOS (Apple Silicon) または Linux(Raspberry Pi 4を含むDebian系などで動作確認)
  - チップ情報・メモリ情報の取得方法はOSごとに異なります
    (macOS: `sysctl` / `vm_stat`、Linux: `/proc/cpuinfo` / `/proc/meminfo`)
- Python 3.9以降
- ローカルLLMバックエンドとして、以下のどちらか(または両方)が動作していること
  - [Ollama](https://ollama.com/): `ollama serve` (通常は自動起動) が起動していること
  - [LM Studio](https://lmstudio.ai/): アプリ内の「Local Server」機能を起動していること
    (既定ポート`1234`のOpenAI互換API。`lms server start` でも起動できます)。
    **Local Serverの設定で「Require Authentication」がONになっていると、
    Yoriaiは認証ヘッダーを付けずに問い合わせるため401エラーになり、
    モデル一覧が常に空になります。OFFにしておいてください。**
  - どちらも動いていない場合、モデル一覧は空のまま自己紹介カードが生成されます(エラーにはなりません)

## セットアップ

### 方法1: セットアップスクリプトを使う(おすすめ)

venv作成・依存関係インストール・トークン設定・常駐化登録までを対話的にまとめて行う
スクリプトを用意しています。

```bash
git clone <このリポジトリのURL>
cd yoriai
./scripts/setup.sh
```

「新しい組織を作る/既存の組織に参加する/あとで自分で設定する」を選ぶ画面が出るので、
案内に沿って進めてください。最後に「常駐化しますか?」と聞かれるので、
ログアウト後も動かし続けたい場合は `y` と答えてください(常駐化については
後述の「常駐化(自動起動)」の節も参照してください)。

### 方法2: 手動でセットアップする

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

この場合、トークンの設定(`--init`/`--join`)や常駐化(`scripts/launchd`/`scripts/systemd`)は
このあとの節を参照して個別に行ってください。

## 実行方法

Yoriaiは起動前に「トークン(組織の合言葉)」が必要です。まずどちらかの操作でトークンを用意してください。

### 1. 新しい組織を作る(初回の1台だけ)

```bash
python3 yoriai.py --init
```

対話的に合言葉(トークン)の入力を求められます。好きな文字列を入力するとそれが
そのまま合言葉になります。何も入力せず空欄でEnterを押すと、ランダムなトークンが
自動生成されます。合言葉を先に決めておきたい場合は、引数で直接指定することもできます。

```bash
python3 yoriai.py --init="うちの合言葉"
```

決まった合言葉/トークンはコンソールに表示されます。これをメモしておき、
同じ組織に参加させたい他のMacに共有してください。
`--init` はトークンの発行・保存のみを行い、エージェントの起動は行いません
(理由は後述の「実装上の判断メモ」を参照)。

既にトークンを発行済みの状態で `--init` を実行しても、新しいトークンには**上書きされません**。
その場合は既存のトークンがそのまま表示されるだけです。

```
既にこの組織のトークンが存在します: <既存のトークン>
このMacでYoriaiを開始するには: python yoriai.py
トークンを再発行したい場合は: python yoriai.py --init --force
```

どうしても新しいトークンを発行し直したい場合は `--force` を付けてください。
既存の組織との接続が切れる旨の確認プロンプトが表示され、`y` と答えた場合のみ上書きされます。

```bash
python3 yoriai.py --init --force
```

### 2. 既存の組織に参加する

```bash
python3 yoriai.py --join=<共有されたトークン>
```

指定したトークンを保存したうえで、そのままエージェントとして起動します。

### 3. 2回目以降の起動(トークン保存済みの場合)

```bash
python3 yoriai.py
```

保存済みのトークンを使ってそのまま起動します。トークンが未設定の場合は
`--init` か `--join` を促すメッセージを表示して終了します。

起動すると、以下が行われます。

- 自己紹介カードをHTTPで配信するローカルサーバーが起動します
  (既定ポートは `47120`。詳細は後述の「ポートを指定したい場合」を参照)。
- mDNSは物理LANインターフェース(`en0`など)のIPアドレスのみを使って、
  `_yoriai._tcp.local.` というサービスとして自分自身を登録します
  (広告するのはトークンそのものではなく、トークンから計算したハッシュ値のみです)。
  Tailscaleの仮想インターフェース(`utun*`)は自動的に除外されます。
  どのインターフェース/IPアドレスを使っているかは起動時のログに表示されます。
- 同時に、同じサービスタイプを名乗る他のエージェントをLAN内で探索します。
  発見がない間も、10秒おきに「探索中... (現在発見数: mDNS N件 / Tailscale M件)」
  というログが出るため、正常に動作中であることを外から確認できます。mDNS側の件数は
  発見・消失のたびに更新されるリアルタイムの値です。Tailscale側の件数も後述の通り
  30秒ごとに再スキャンして更新されます。
- 発見した相手のトークン(のハッシュ値)が自分と一致する場合のみ、その `/card` エンドポイントに
  HTTPでアクセスして自己紹介カード(JSON)を取得し、以下のようにログへ表示します。
  トークンが異なる相手は「別の組織のエージェント」としてログにだけ記録し、無視します。

```
2026-08-18 10:00:00 [INFO] 🤝 MacBookPro-xxxx を発見しました (192.168.1.23:54321)
    チップ: Apple M2 Pro
    空きメモリ: 89.2GB / 総メモリ: 96.0GB
    ロード済みモデル: qwen2.5:14b
    インストール済みモデル(3件): qwen2.5:14b, llama3.1:8b, gemma2:9b
```

- さらに、Tailscaleが導入されていれば `tailscale status --json` でピア一覧を取得し、
  各ピアの `/card` エンドポイントに直接アクセスを試みます(mDNSとは別枠の仕組みです)。
  起動直後に1回、その後は30秒ごとに再スキャンします(相手がまだ起動しきっていない
  タイミングで一度失敗しても、後で自動的に見つかるようにするためです)。
  Tailscale CLIはPATH上の`tailscale`だけでなく、GUI版(App Store/dmg配布)のアプリバンドルや
  Homebrewでの典型的な設置場所も探すため、どこにインストールしていても
  「Tailscale CLIを検出しました: /Applications/...」のようにログで確認できます。
  トークンが一致する応答があった場合は mDNS と同様のログに `🌐 [Tailscale]` のラベルが付いて表示され、
  最後に「Tailscale経由でN台のエージェント候補を確認しました」とまとめて表示されます。
  問い合わせに失敗したピアがいる場合は、トークン不一致(403)なのか接続できないのかが分かるよう、
  ピアごとに失敗理由もログに表示されます。Tailscale未導入の場合はスキップされ、エラーにはなりません。

終了する場合は `Ctrl+C` を押してください。mDNSサービスの登録解除とサーバーの停止まで行われます。

### ポートを指定したい場合

自己紹介カードサーバーの既定ポートは `47120` です。Tailscale経由の発見は
相手も既定ポートで待ち受けている前提で問い合わせるため、通常は変更不要です。

```bash
python3 yoriai.py --port 8765
```

同一マシン上で複数のエージェントを起動してテストしたい場合など、
ポートの衝突を避けたいときは `--port 0` を指定するとOSに空きポートを自動選択させられます
(この場合、Tailscale経由の発見の対象にはなりません)。

```bash
python3 yoriai.py --port 0
```

## 2台のMacで動作確認する手順

1. 両方のMacでOllamaまたはLM Studioのどちらかが動作しており、少なくとも1つはモデルを
   用意していることを確認してください(Ollamaなら`ollama pull qwen2.5:7b`など、
   LM StudioならGUIでモデルをダウンロードし「Local Server」を起動しておきます)。
2. 両方のMacが同じLAN(同じWi-Fi/有線ネットワーク)に接続されていることを確認してください。
   ※ mDNSはブロードキャストベースのため、異なるサブネットやゲストネットワーク分離のあるWi-Fiでは
   発見できないことがあります。Tailscaleを導入している環境では、mDNSは物理LANインターフェース
   (`en0`など)のみを使うため、Tailscaleの接続状態は同一LAN内でのmDNS発見には影響しません。
3. このリポジトリを両方のMacにcloneし、それぞれで依存関係をインストールします。

   ```bash
   git clone <このリポジトリのURL>
   cd yoriai
   python3 -m venv .venv && source .venv/bin/activate
   pip install -r requirements.txt
   ```

4. Mac Aで新しい組織のトークンを発行します。

   ```bash
   python3 yoriai.py --init
   ```

   表示されたトークン(64文字の16進文字列)をコピーしておきます。

5. Mac Aで、発行したトークンを使ってそのままエージェントを起動します。

   ```bash
   python3 yoriai.py
   ```

   (`--init` はトークン発行のみで起動しないため、別途この起動コマンドを実行します。)

6. Mac Bで、Mac Aから共有されたトークンを指定して参加します。

   ```bash
   python3 yoriai.py --join=<Mac Aで発行されたトークン>
   ```

   `--join` はトークンの保存と同時にエージェントを起動します。

7. 数秒以内に、両方のターミナルにお互いを発見したログ(🤝 ...を発見しました)が表示されれば成功です。
   モデルをロードした状態(例: `ollama run qwen2.5:14b` を実行中)で試すと、
   「ロード済みモデル」欄に反映されることも確認できます。
8. 片方を `Ctrl+C` で終了すると、もう片方のログに「エージェントが見えなくなりました」と表示されます
   (mDNSのTTL/更新のタイミングにより、反映まで数秒〜数十秒かかる場合があります)。

### トークンが異なる場合の動作を確認したい場合

Mac Bで異なるトークン(例: `python3 yoriai.py --join=0000...`のような適当な文字列)を指定して起動すると、
Mac A側のログに「🔒 ... は別の組織のエージェントのようです(トークン不一致のため無視します)」と表示され、
カードの交換は行われないことを確認できます。

### Tailscale経由での発見を確認したい場合

同じLANにいなくても、両方のMacがTailscaleで同じTailnetに参加していればTailscale経由で発見できます。

1. 両方のMacでTailscaleにログインし、同じTailnetに参加していることを確認します
   (`tailscale status` でお互いが見えていればOKです)。
2. 双方とも既定ポート(`47120`)のまま `python3 yoriai.py`(または`--init`/`--join`)で起動します
   (`--port` で別ポートを指定していると、Tailscale経由の発見では見つけられません)。
3. 起動時のログに「Tailscale経由でN台のエージェント候補を確認しました」と表示され、
   相手が見つかった場合はそのすぐ上に `🌐 [Tailscale] ... を発見しました` という
   詳細ログ(mDNSでの発見と同じ形式)が表示されます。
4. Tailscaleが導入されていないMacで試すと、「tailscaleコマンドが見つからないため、
   Tailscale経由の発見はスキップします。」と表示され、エラーにはならずmDNSでの発見のみ継続します。

### うまく発見できない場合のチェックポイント

- macOSのファイアウォールでPythonのネットワーク受信が許可されているか
  (初回実行時に許可ダイアログが出ることがあります)。
- 2台が同じサブネットにいるか(ルーターのゲストWi-Fi/クライアント分離設定に注意)。
- `ollama serve` が起動しているか(`curl http://localhost:11434/api/tags` で確認できます)。
- (mDNSの場合)起動時のログに物理LANインターフェースのIPアドレスが表示されているか
  (「物理LANインターフェース(en\*)を特定できなかったため」という警告が出ていないか)。
- (Tailscale経由の場合)双方とも既定ポート(`47120`)で起動しているか。

## Raspberry Pi(Linux)での動作確認手順

1. Raspberry Pi 4(Debian系、Raspberry Pi OSなど)にPython 3.9以降がインストールされていることを確認します。

   ```bash
   python3 --version
   ```

2. このリポジトリをclone/転送し、依存関係をインストールします。

   ```bash
   git clone <このリポジトリのURL>
   cd yoriai
   python3 -m venv .venv && source .venv/bin/activate
   pip install -r requirements.txt
   ```

3. トークンを用意します(既に組織がある場合は`--join`、新規なら`--init`)。

   ```bash
   python3 yoriai.py --join=<共有されたトークン>
   ```

4. 起動ログで、チップ情報が `/proc/cpuinfo` から取得したボード名
   (例: `Raspberry Pi 4 Model B Rev 1.4`)になっているか、メモリ情報が
   `/proc/meminfo` ベースの値になっているかを確認します。
5. Mac側のYoriaiと同様に、mDNS(同一LAN内)またはTailscale経由でお互いを発見できるか確認します。
   Raspberry PiのmDNS向け物理LANインターフェース検出は、macOS版のような許可リストではなく、
   既知の仮想インターフェース(`tailscale*`, `docker*`, `veth*`など)を除外するブロックリスト方式です
   (詳細は後述の判断メモを参照)。`ip`/`ifconfig`コマンドが入っていない最小構成でも、
   Python標準ライブラリだけで動作するように作っています。

## 常駐化(自動起動)

SSHセッションを切っても動き続け、クラッシュ時は自動的に再起動されるように、
OSごとの常駐化スクリプトを `scripts/` 以下に用意しています。

**重要**: 常駐化スクリプトを実行する前に、必ず `--init` または `--join` で
トークンを保存しておいてください。トークン未設定のまま常駐化すると、
`python3 yoriai.py`(引数なし)が起動のたびにすぐ終了し、
launchd/systemdが再起動を繰り返してしまいます。

### macOS(launchd)

```bash
./scripts/launchd/install.sh
```

ユーザーのLaunchAgentとして `~/Library/LaunchAgents/com.yoriai.agent.plist` に登録されます。
ログイン時に自動起動し、異常終了(クラッシュ)時は自動再起動されます
(`launchctl`のKeepAlive設定。正常終了時=`Ctrl+C`相当では再起動しません)。
ログは `~/.yoriai/logs/agent.log` / `agent.error.log` に出力されます。

```bash
# 状態確認
launchctl list | grep com.yoriai.agent

# 一時停止・再開
launchctl unload ~/Library/LaunchAgents/com.yoriai.agent.plist
launchctl load ~/Library/LaunchAgents/com.yoriai.agent.plist

# アンインストール
./scripts/launchd/uninstall.sh
```

### Linux(systemd、Raspberry Pi 4など)

```bash
./scripts/systemd/install.sh
```

システム全体のsystemdサービス(`/etc/systemd/system/yoriai.service`)として登録されるため、
`sudo`のパスワード入力を求められます。OS起動時に自動起動し、異常終了時は
5秒後に自動再起動されます(`Restart=on-failure`)。

```bash
# 状態確認
sudo systemctl status yoriai.service

# ログ確認
sudo journalctl -u yoriai.service -f

# 一時停止・再開
sudo systemctl stop yoriai.service
sudo systemctl start yoriai.service

# アンインストール
./scripts/systemd/uninstall.sh
```

### アップデート

Yoriaiは今後も頻繁に更新する想定のため、最新のコードを取り込む・依存関係を更新する・
(常駐化している場合は)サービスを再起動する、を1コマンドでまとめて行うスクリプトを用意しています。

```bash
./scripts/update.sh
```

- `git fetch` + fast-forwardのみのmergeでコードを更新します。ローカルに未コミットの変更や、
  originから分岐したコミットがある場合は、force的に上書きせずエラーで停止します
  (安全のため、コンフリクトの自動解決はしません)。
- `requirements.txt` の依存関係を更新します(`.venv` があればそちらの `pip` を使います)。
- 常駐化サービス(launchd/systemd)が登録されていれば自動的に再起動します。
  登録されていない場合は案内メッセージを出すだけで、フォアグラウンド実行中のプロセスを
  勝手に止めたりはしません(手動で `Ctrl+C` して再起動してください)。

## 実装上の判断メモ(仮決め箇所)

今回の実装で判断に迷い、ひとまずこう決めた箇所を残しておきます。次フェーズで見直す際の参考にしてください。

- **「空きメモリ」の定義**: `vm_stat` の `Pages free + Pages inactive` を空きメモリとみなしています
  (`yoriai.py` の `_parse_vm_stat_free_bytes`)。macOSは積極的にメモリをキャッシュに使うため、
  `Pages free` だけを見ると実態よりかなり少なく表示されてしまうための仮の判断です。
  より正確な「今すぐ使える空き容量」が必要になった場合は `memory_pressure` コマンドの利用も検討してください。
- **チップ情報の取得方法**: `sysctl -n machdep.cpu.brand_string` を利用しています。
  Apple Silicon Mac上ではネイティブに正しいチップ名(例: `Apple M2 Pro`)が返る前提です。
- **HTTPポート**: 当初は既定でOSに空いているポートを自動選択させていましたが、
  フェーズ2.5でTailscale経由の発見(相手のポート番号を事前に知る必要がある)を追加したため、
  既定ポートを固定値(`47120`)に変更しました。`--port 0` で従来通りの自動選択にも戻せます。
- **mDNSサービスインスタンス名の衝突回避**: `<ホスト名>-<agent_idの先頭8文字>` という名前で登録しています。
  同じホスト名のマシンが複数ある場合や、同一マシンで複数プロセスを起動するテストケースを想定した仮の判断です。
- **自己紹介カードの鮮度**: `/card` エンドポイントはリクエストごとにその場でメモリ/モデル情報を再取得します。
  キャッシュは行っていないため、ピア側は常に最新のスペックを取得できますが、
  多数のエージェントから同時に叩かれる状況は今回のスコープでは考慮していません。
- **認証なし**: 今回は誰でも `_yoriai._tcp.local.` を名乗れば発見・カード取得ができる状態です。
  トークンによる参加制限は次フェーズで追加予定です。

### フェーズ2(トークンによる参加制御)で判断に迷った箇所

- **トークンの保存先**: `~/.yoriai/config.json` への平文保存です(せめてファイルパーミッションは
  所有者のみ読み書き可能に絞っています)。当初はmacOS Keychainを優先する設計でしたが、
  フェーズ3で個人のローカル/Tailscaleネットワーク内での利用を前提に、運用のしやすさを優先して
  平文ファイル保存に統一しました(詳細は後述の「フェーズ3」を参照)。実装は `config.py` を参照してください。
- **mDNS/HTTPで流すのは生トークンではなくハッシュ値**: mDNSのTXTレコードは同一ネットワーク上の
  誰からでも読めてしまうため、生トークンをそのまま広告すると「トークンによる参加制限」の意味が
  薄れてしまいます。そのため `SHA-256(トークン)` の値(`org_fingerprint`)だけを広告し、
  自己紹介カードを取得する際のHTTPリクエストにも同じ値をヘッダー(`X-Yoriai-Org-Fingerprint`)で
  付与する方式にしました。生トークンが第三者に見える経路は「人が直接トークン文字列を共有する」
  ときだけ、という設計です。ただし、SHA-256のハッシュ値自体は毎回固定のため、
  厳密な意味でのなりすまし対策(リプレイ攻撃対策など)にはなっていません。今回のスコープでは
  「同じLAN上の別組織を誤って発見・混同しない」ことを目的とした簡易フィルタと位置づけています。
- **`/card` エンドポイントのサーバー側検証**: mDNSの発見時点でトークン不一致の相手はそもそも
  カードを取りに行かない設計ですが、`/card` に直接HTTPアクセスされた場合の備えとして、
  サーバー側でも `X-Yoriai-Org-Fingerprint` ヘッダーを検証し、不一致・未指定なら403を返すようにしています。
- **`--init` は起動しない**: トークンの発行・保存だけを行い、そのままエージェントとしては起動しない
  仕様にしました。発行したトークンを他のMacに共有してから、あらためて `python yoriai.py` を
  実行するという2段階の操作の方が、意図せず古いトークンで動き続けたり、
  共有前に他人に発見されたりする事故を避けやすいと判断したためです。
- **トークンのローテーション/失効は未実装**: 一度発行・共有したトークンを無効化する仕組みは
  今回のスコープには含めていません。トークンが漏れた場合は `--init --force` で新しいトークンを
  再発行し、全メンバーに `--join` し直してもらう運用が現状の想定です(次フェーズで見直し予定)。
- **`--init` の再実行時に無条件で上書きしない**: 当初は `--init` のたびに新しいトークンを
  発行・上書きしていたが、既存の組織のメンバーが知らないうちにトークンが変わってしまい
  接続が切れる事故につながるため修正した。既存トークンがある場合はそれを表示するだけにとどめ、
  意図的に再発行したい場合だけ `--force` と確認プロンプトへの `y` 応答を必須にしている。
  確認入力を受け取れない状況(非対話実行など)では安全側に倒して「上書きしない」扱いにしている。

### フェーズ2.5(mDNS修正 + Tailscale経由の発見)で判断に迷った箇所

- **mDNSを物理LANインターフェース(`en*`)に限定した理由**: Tailscale導入環境では、
  mDNSがTailscaleの仮想インターフェース(`utun*`)にもバインドされ、"No route to host" のような
  エラーが発生して同一LAN内の発見すら失敗するケースがあった。macOSで物理イーサネット/Wi-Fiに
  使われる `en<数字>` という命名規則のインターフェースだけを `ifconfig` の出力から拾い、
  zeroconfの `interfaces` にIPアドレスのリストとして渡すことで、Tailscaleなどの仮想
  インターフェースを除外している。`ifconfig` の出力を素朴に正規表現でパースしているだけの
  簡易的な実装であり、環境によっては正しく拾えない可能性がある(その場合は警告ログを出したうえで
  全インターフェースにフォールバックする)。
- **既定ポートを固定値にした理由**: Tailscale経由の発見はmDNSのようにサービス自体からポート番号を
  教えてもらえないため、相手も既定ポート(`47120`)で待ち受けている前提で問い合わせる方式にした。
  そのため既定のポート選択を「OSに自動選択させる」から「固定値」に変更した。同一マシン上での
  複数エージェント起動など、自動選択が必要な場合は `--port 0` で明示的に元の挙動に戻せる。
- **Tailscale経由の発見を定期的に再スキャンするようにした理由**: 当初は起動時に1回だけ
  スキャンする仕様にしていたが、実機検証で「片方を起動した瞬間、もう片方のYoriaiがまだ
  起動しきっていなかった(ポートがまだlistenされていない)」タイミングでスキャンしてしまい
  `Connection refused`で失敗し、その後相手が起動を完了しても再スキャンしないため
  ずっと0件のまま固定されてしまう問題が見つかった。そこで起動直後の1回に加えて、
  `TAILSCALE_RESCAN_INTERVAL_SEC`(既定30秒)ごとに再スキャンするようにした。
  mDNSのハートビートと同じ10秒間隔にしなかったのは、ピア数が多いTailnet
  (検証時は11台前後)では毎回全ピアに問い合わせが走り、ログが読みづらくなる・
  ネットワーク負荷が増えることを避けるためで、実用上は30秒でも十分実用的だと判断した。
- **Tailscale未導入環境でのふるまい**: `tailscale.find_cli()` でコマンドの有無を確認し、
  見つからない場合は例外を投げずにTailscale経由の発見をスキップする設計にした(`tailscale.py`)。
  Tailscaleを使わない組織/メンバーがいても、mDNSでの発見には一切影響しない。
- **Tailscale CLIの探索先を複数用意した理由**: 当初はPATH上の`tailscale`コマンドのみを
  見ていたが、App Store版/dmg配布のGUI版Tailscaleを使っている環境ではCLIがPATHに出てこず、
  常にスキップ扱いになってしまっていた。`/usr/local/bin/tailscale`へのシンボリックリンクで
  回避しようとしたところ、GUI版のバイナリはアプリバンドルとしての起動を前提にしているらしく
  "Fatal error: The current bundleIdentifier is unknown to the registry" で失敗することを
  確認したため、シンボリックリンクは使わない方針にした。代わりに (1) PATH上の`tailscale`、
  (2) GUI版のアプリバンドル内バイナリを絶対パスで直接指定
  (`/Applications/Tailscale.app/Contents/MacOS/Tailscale`)、(3) Homebrewでの典型的な設置場所
  (`/usr/local/bin`、`/opt/homebrew/bin`)の順に探し、見つかったパスを起動時のログに表示する
  ようにした。これでもインストール場所が特殊な環境では見つからない可能性が残る。
- **見つかったパスを`os.path.realpath()`で実体パスに解決する理由**: 上記の対策後も、
  実機で "Tailscale CLIを検出しました: /usr/local/bin/tailscale" の直後に
  "Fatal error: The current bundleIdentifier is unknown to the registry" で
  失敗するケースが見つかった。原因は、GUI版Tailscaleアプリの「Install command-line tool」
  設定により `/usr/local/bin/tailscale` にアプリバンドル内バイナリへのシンボリックリンクが
  自動生成されており、`shutil.which("tailscale")` がPATH経由でこのシンボリックリンクを
  真っ先に見つけてしまい、アプリバンドルの実体パスを直接指定するという当初の対策より前に
  返ってしまっていたため。見つかったパスがPATH経由・候補パス経由のどちらであっても
  `os.path.realpath()` で実体パスに解決してから呼び出すようにし、シンボリックリンク経由の
  起動を確実に避けるようにした。
- **Tailscale経由の問い合わせ失敗をログに出すようにした理由**: 当初は「オフラインのピアや
  Yoriaiを起動していないピアの方が多い想定」で、ピアごとの問い合わせ失敗は静かにスキップして
  いた。しかし実機検証で、片方のMacからはもう片方を発見できるのに、逆方向は
  「Tailscale経由で0台のエージェント候補を確認しました」としか出ず、原因(トークン不一致で
  403なのか、そもそも繋がらないのか)が全く分からず切り分けに苦労した。そこで、
  `tailscale status`で見つかったピア一覧をまず表示し、各ピアへの問い合わせが失敗した場合は
  その理由(HTTPステータスや接続エラーの内容)をINFOログに出すようにした。Tailscaleの
  ピア数は通常それほど多くない想定のため、ログが読みづらくなるほどのノイズにはならないと判断した。
- **ハートビートログにTailscale発見数も表示した理由**: 実際に2台のMac(Mac mini/Mac Studio)で
  検証したところ、ルーター側の設定(クライアント間のマルチキャスト遮断と思われる)により
  mDNSがネットワークレベルで一切機能しない環境があることが判明した
  (`dns-sd -B _yoriai._tcp` や `_ssh._tcp` などmacOS標準のBonjourブラウザでも
  互いを発見できないことを確認済み)。そのような環境ではmDNSの発見数が常に0件のままになり、
  ハートビートログだけを見ると「本当に0台なのか、何かが壊れているのか」が分かりにくい。
  そこで、Tailscale経由の発見数もあわせて表示するようにした。Tailscale側は
  `TAILSCALE_RESCAN_INTERVAL_SEC`(既定30秒)ごとに再スキャンして更新されるため、
  この数字も時間が経てば最新の状況を反映する。

### LM Studio対応で判断に迷った箇所

- **OllamaとLM Studioの両方に問い合わせて合算する方式にした理由**: 実際に使う2台が
  どちらもLM Studioだった、という報告を受けて対応した。「どちらか一方だけに対応する」
  のではなく、Ollamaの`/api/tags`・`/api/ps`とLM Studioの`/v1/models`(OpenAI互換API)の
  両方に問い合わせ、どちらか(または両方)が動いていればモデル一覧に反映されるようにした。
  同じモデル名が両方から返ってきた場合は重複排除している。動いていないバックエンドへの
  問い合わせは(Ollama用のコードと同様に)警告ログを出すだけでエラーにはしない。
- **LM Studioは「インストール済み」と「ロード済み」を区別していない理由**: LM Studioの
  OpenAI互換API(`/v1/models`)は、Ollamaの`/api/tags`(インストール済み一覧)と
  `/api/ps`(ロード済み一覧)のような区別を提供していない。そのため、LM Studioから
  取得できたモデルは仮の判断として「インストール済み」「ロード済み」の両方に含めている。
  より正確なロード状態が必要になった場合は、LM Studioのバージョンによって利用可能な
  `/api/v1/models`(ネイティブAPI、`state`フィールドでロード状態を区別できる)への
  切り替えを次フェーズで検討する。
- **LM Studioの既定ポートは`1234`固定**: LM StudioのLocal Server機能の既定ポートを
  そのまま使っている。Ollamaの`11434`と同様、ポート変更に対応する設定項目は
  今回のスコープには含めていない。
- **既知のハマりどころ: LM Studioの「Require Authentication」設定**: 実機検証で、
  LM Studioのサーバー自体は起動しているのに自己紹介カードのモデル一覧が常に空になる、
  という事象が発生した。原因はLM StudioのLocal Server設定で
  「Require Authentication」がONになっていたこと。Yoriaiは現状APIキー/認証ヘッダーを
  一切送らずに`/v1/models`を叩く実装(今回のスコープでは認証の仕組みは実装しない、という
  当初の方針通り)のため、認証必須の設定だと401で弾かれ、`get_lmstudio_models()`が
  例外を握りつぶして空リストを返していた。LM Studio側でこの設定をOFFにすることで解決した。

### フェーズ3(トークン運用のシンプル化)で判断に迷った箇所

- **Keychain保存の廃止**: 個人のローカル/Tailscaleネットワーク内での利用が前提であり、
  厳重なセキュリティよりも運用のしやすさ(合言葉を人に伝えやすい、設定ファイルを直接見て
  確認・編集できる、など)を優先することにした。macOS Keychain連携のコード(`security`
  コマンドの呼び出し)は削除し、`~/.yoriai/config.json` への平文保存に一本化した。
  なお、mDNS/HTTP上で流すのは引き続きSHA-256でハッシュ化した値のみで、生トークンを
  ネットワークに流さない設計は変更していない。
- **`--init` の合言葉指定方法を「引数 + 対話入力」の2通りにした理由**: `--init=<合言葉>`
  による直接指定は、スクリプトからの利用や複数台へ手早く展開したい場合に便利な一方、
  端末の履歴やスクリーンショットに合言葉が残りやすいという弱点がある。対話入力
  (`--init` を値なしで実行)はその場でしか見えないため、状況に応じて使い分けられるよう
  両方を用意した。対話入力で何も入力しなかった場合は、従来通りランダムな32バイトの
  トークンにフォールバックする(依頼にあった仕様通り)。
- **合言葉の形式チェックはしていない**: 空白のみの入力は無効(トリムして空ならランダム
  生成にフォールバック)とした以外、長さや文字種の制限は設けていない。短すぎる合言葉は
  推測されやすくなるが、今回のスコープでは利用者の判断に委ねることにした。

### フェーズ4(Linux対応 + 常駐化)で判断に迷った箇所

- **Linuxのメモリ情報にMemAvailableを使う理由**: `/proc/meminfo` には `MemFree`(本当に
  何にも使われていないメモリ)と `MemAvailable`(キャッシュなどを解放すれば新規プロセスに
  割り当てられる量の推定値)の両方がある。macOS版で「Pages free + Pages inactive」を
  「空きメモリ」とみなした判断と一貫性を持たせるため、Linux版でも `MemFree` 単体ではなく
  より実態に近い `MemAvailable` を使うことにした。
- **Linuxの物理LANインターフェース検出を許可リストではなくブロックリストにした理由**:
  macOS版は物理イーサネット/Wi-Fiが `en<数字>` という命名規則にほぼ統一されているため
  許可リスト方式で十分だったが、Linuxは `eth0`, `wlan0`, `enp3s0`, `wlp2s0` など機種や
  ディストリビューションによって命名がまちまちで、許可リストだと拾いこぼす可能性が高い。
  そのため逆に、既知の仮想インターフェース(`lo`, `tailscale*`, `docker*`, `veth*`, `br-*`,
  `virbr*`, `tun*`, `tap*`, `wg*`)だけを除外するブロックリスト方式にした。想定していない
  仮想インターフェースがあれば拾ってしまう可能性は残る。
- **`ip`/`ifconfig`コマンドを使わず標準ライブラリだけで実装した理由**: Raspberry Pi OS Lite
  などの最小構成では `iproute2`/`net-tools` が入っていないことがある。そこで
  `socket.if_nameindex()`(インターフェース一覧)と `fcntl.ioctl(SIOCGIFADDR)`
  (各インターフェースのIPv4アドレス取得、Linux固有のシステムコール)を組み合わせ、
  外部コマンドに一切依存しない実装にした。
- **常駐化はmacOS=ユーザーLaunchAgent、Linux=システムsystemdサービスにした理由**:
  「ログアウト後も動き続ける」という要件に対して、launchdのユーザーエージェントは
  ログイン中は問題なく動くため素直に採用した。一方Linuxのユーザーセッションsystemd
  (`systemctl --user`)はログアウトすると既定で停止してしまい、`loginctl enable-linger`
  という追加設定をしないと動き続けない。設定を1つ増やすよりは、最初から
  システム全体のsystemdサービス(`/etc/systemd/system/`、要sudo)として登録する方が
  「ログアウト後も動き続ける」を単純に満たせると判断した。
- **クラッシュ時のみ自動再起動する設定にした理由**: launchdは`KeepAlive`を
  `{SuccessfulExit: false}` にし、systemdは`Restart=on-failure`にすることで、
  異常終了(クラッシュ、非0の終了コード)の場合だけ自動再起動し、正常終了
  (終了コード0)の場合は再起動しないようにした。ただし、トークン未設定のまま
  `python3 yoriai.py` を実行すると `sys.exit(1)`(異常終了扱い)で終了する仕様のため、
  常駐化スクリプトを実行する前に必ずトークンを用意しておく必要がある、という
  制約が生まれている(README本文に注記済み)。
- **常駐化スクリプトの配置場所を`scripts/`以下にした理由**: 将来的にOSやツールが
  増えても整理しやすいよう、`scripts/launchd/`・`scripts/systemd/`という
  OS別ディレクトリに分けた。テンプレートファイル(`.plist.template`/`.service.template`)
  と、`sed`でプレースホルダー(`__PYTHON_BIN__`など)を実際のパスに置換して配置する
  `install.sh`/`uninstall.sh`という構成に統一している。
- **`update.sh`でforce的な上書きをしない理由**: 頻繁に更新する運用を想定して
  `git fetch` + `git merge --ff-only` を使っている。`git pull`や`git reset --hard`で
  常に強制上書きする方法も検討したが、ローカルでの調査・一時的な変更を
  意図せず消してしまう事故を避けるため、fast-forwardできない(履歴が分岐している)
  場合はエラーで止めて利用者に判断を委ねる設計にした。同じ理由で、依存関係の
  更新やサービス再起動も「壊れていたら止める」方針にしており、途中で失敗したら
  それ以降のステップ(サービス再起動など)は実行されない(`set -euo pipefail`)。
- **`setup.sh`の「参加する」選択肢で`--join`をそのまま呼ばない理由**: `--join`は
  トークンを保存すると同時にエージェントをフォアグラウンドで起動する仕様
  (READMEの「実行方法」参照)。セットアップウィザードの最後には常駐化するかどうかの
  質問が控えているため、ここでエージェントを起動してしまうとフォアグラウンドの
  プロセスとその後の常駐化サービスがポートを取り合ってしまう。そのため「参加する」の
  場合は環境変数経由で`config.save_token()`を直接呼び、保存だけ行ってエージェントは
  起動しない設計にした。「新しい組織を作る」の`--init`は元々起動しない仕様なので、
  そのまま`yoriai.py --init`に委譲している(合言葉の対話入力もそちらの仕組みを再利用)。
- **常駐化前にトークンの有無を確認する理由**: 常駐化スクリプト自体もトークン未設定だと
  再起動を繰り返してしまう(既知の制約、常駐化の節に記載)。`setup.sh`では
  常駐化する直前にもう一度トークンの有無を確認し、無ければ常駐化をスキップして
  案内メッセージを出すようにした。
